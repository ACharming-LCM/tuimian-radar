## 问题 1：bundle 是快照，接远程库会分叉

**B 的担心是对的，而且比他想的更严重 —— 这是我的疏漏。**

我在 `814aa48` 打了第一份 bundle 发给 B，之后**又提交了 5 次**：

```
9184fbe 数据层完善：解析失败 16->1、deadline 28%->31%、修掉 http/https 重复记录
2446aaf C: journal 追加收工复核

42cdd60 faculty: 生成人类可读导师名册
a686d9f 导师层：浙大物理学院 50 位导师
```

其中 **`contracts/api.md`、`contracts/fixtures/notices.list.json`、
`contracts/fixtures/match.response.json` 都变了。**

意思是：B 如果现在照着 clone 里的 `api.md` 写 `/api/match`，
他会**对着过期的契约写**，而且 `match.response.json` 里还缺
`extract.confidence` / `has_attachments` / `attachments_count` 三个字段。

**结论：必须发新 bundle（已打，`tuimian-20261017-v2.bundle`，943 KB @ 9184fbe）。**

B 的本地提交**不会白做**：他的提交只动 `server/`，
我的 5 个提交只动 `contracts/` `collector/` `docs/` `data/` `web/`，
**路径不重叠，rebase 不会冲突。**

```powershell
cd D:\tuimian
git fetch <下载路径>\tuimian-20261017-v2.bundle main
git rebase FETCH_HEAD          # 预期 0 冲突；路径不重叠
git log --oneline -3           # 顶上应该是你的提交，下面是 9184fbe
```

**教训（我记下了）**：给别人发快照的那一刻，就等于承诺"之后不再改契约"。
做不到的话，必须**同时给出补丁或新快照**，否则对方是在流沙上盖房子。
以后发快照的提交里要写清"本快照之后如有契约变更，会补发 patch"。

## 问题 2：`deadline` 那 70% 的缺口要不要靠 LLM

**B 的判断是对的，我同意"今晚不做"。** 我在 journal 里写了"剩下的靠 LLM（B 的活）"，
却在 `B-KICKOFF.md` 的任务表里**完全没排这一项** —— 那是我的不一致，不是 B 漏看。

**决定：**

1. **今晚不接 LLM。** 接口如实返回 `deadline: null` + `warnings` 里写明
   "未抽到截止日期，务必点开原文确认"。**这是诚实且可交付的状态。**
2. 已把这条写进 `B-KICKOFF.md` 的**「明确不做的」清单**（之前它只是"没写"，
   而"没写"会被三个人理解成三件不同的事）。

**如果以后要做，唯一可接受的形态是"抽取"，不是"生成"：**

| 允许 | 禁止 |
|---|---|
| 让 LLM 从原文里**挑出已经存在的日期字符串**，并返回它所在的原句 | 让 LLM **推算/推断**一个日期 |
| 返回里必须带 `source_span`（原文片段），前端可点开核对 | 只给一个日期、指不回原文 |
| `extract.method = "llm"`，置信度单独给，前端标「疑似」 | 和规则抽取的结果混在一起、看不出出处 |

理由：**用户会拿这个日期去安排时间。** 一个编造的截止日比 `null` 危险得多 ——
`null` 用户会去点原文，编造的日期用户会信。

**仍未定（需要团队拍板，不该 B 一个人扛）：** 用哪个模型、key 谁出、有没有预算。

**流程教训**：改 fixtures 等于改契约。以后这类改动**先发一条通知，再改**，
哪怕只是条数变了。
