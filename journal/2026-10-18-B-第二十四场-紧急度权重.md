### 三、实现

**① `urgency_weight(item)`** —— 分档照派单给的（`2.0/1.5/1.2/1.0`），但**有两处没照做**：

| 派单 | 我做的 | 为什么 |
|---|---|---|
| 已过期 `return 0`，并且**过滤掉** | `return 0.0`，**但不过滤**（沉底） | 见下 |
| `deadline=None → return 1.0` | 同（`absent`/`unknown` 给 1.0） | 同（但理由要写清） |

**为什么不过滤**：这是同一天早些时候刚定的 —— "已截止的**沉底不压掉**"。三条理由已经写进契约：
截止日可能抽错、学校会延期、补发的附件截止后照样有人要。
**排序错了只是某条低几行，压错了用户永远不知道它存在。**

派单要把它改成"不返回"，那是**往回退**。要真不返回，得把 `is_expired` 的沉底逻辑
和契约 §16.5 一起改回来 —— 不能悄悄改一处。

**为什么 `absent`/`unknown` 给 1.0 而不是 0**：`unknown` 是"我们没读到截止日"，
**它可能下周就截止**。给 0 等于把"我们不知道"当成"不用急" ——
正是这套三态要消灭的混淆。

**② 排序键改成 `relevance × urgency_weight`**（派单的公式没错，这是它少数对的地方）：

```python
return (1 if is_expired(item) else 0,      # 已截止沉底（保留）
        -(rel * w),                         # ← 新的
        item.get("at") or "", item.get("event_id") or "")
```

**为什么是乘不是加**：两个不同维度（"像不像招生信息" × "离截止还有多久"）。
乘法有个好性质 —— **低相关的东西不会因为紧急插队**（`0 × 2.0` 还是 0）。
加法会让"极不相关但极紧急"排到"很相关但还早"前面。

**③ item 加 `urgency_weight`，但**不加 `sort_score`**：

派单要给 `sort_score`。**没给** —— 它是**排序的实现细节**，暴露出去前端就会拿它当
"这条有多重要"来显示，然后我在后端调权重（T-14 从 1.5 改 1.4）时屏幕上那个数就变了。
**那是把内部公式变成对外承诺。**

`urgency_weight` 不同：它有独立的产品含义（"离截止还有多急"），前端可以据此显示"7 天内"。
