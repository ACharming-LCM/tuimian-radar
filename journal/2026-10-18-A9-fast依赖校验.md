# A9 fast 的脆弱依赖，改成显式校验（2026-10-18）

## 一、问题

`--fast` 只读每栏第 1 页，其余记录靠**从上一轮产物带过来**（A4 实测：带过 263 条）。
所以它的正确性**依赖"上一轮的 `notices.jsonl` 还在且完整"**，而这个依赖原来是隐式的：

- 上一轮文件被删 → fast 读到 0 条基线 → 写出"只有第 1 页那几百条"的产物，**退出码 0**
- 上一轮被截断（写到一半断电）→ 同上，而且坏行会被 `load_jsonl` 静默跳过
- 后果是"看起来正常的半份数据"，比直接报错危险得多

## 二、改法：启动即校验，不合格就拒绝，**不降级**

`crawl.py::_check_fast_baseline(path)`，四条判据（都很便宜）：

| 判据 | 拒绝原因 |
|---|---|
| 文件存在、非空 | `上一轮产物不存在 / 是空文件` |
| 每行能解析成 JSON 且带 `id`/`url` | `有 N 行损坏 —— 像是被截断过` |
| 条数 ≥ `FAST_MIN_PREV`（100） | `只有 N 条（< 100）—— 不像是完整基线` |
| 文件末尾有换行（原子写会写完整） | `最后一行没有换行符 —— 像是写到一半被中断` |

不满足就以 **exit 3** 退出，并且：

- **不偷偷跑 full**（那会把"我以为我在增量"变成"其实在重抓全站"，WAF 预算说没就没）
- **不降级成"只写第 1 页"**（那就是它本来最危险的行为）
- **不写任何产物文件**

日志明确说清三件事：为什么拒绝、为什么不能凑合、怎么办（先 `--full` 建基线）。

## 三、实测

### 拒绝场景（测试里真跑子进程）

```
python crawl.py --fast --out <不存在路径>
exit=3
日志: ❌ --fast 拒绝启动：上一轮产物不存在：…
      fast 只读每栏第 1 页，其余记录必须从上一轮产物带过来。
      …
**产物文件没有被创建**（不许降级成半份数据）
```

### 正常场景（定时任务 13:03 那次，跑的是带校验的新代码）

```
开始 13:03:03
结束 13:05:04        → 121 秒
产物 1120 条（与上一轮一致）
changes: added 0 / removed 0 / unchanged 1120
```

**121 秒，仍然在 2 分钟量级**，校验本身的开销可以忽略（一次顺序读 + JSON 解析）。

### 一个必须说明的异常

我在 11:54 手工跑的另一次 `--fast` 挂了 **68 分钟**没结束（期间机器休眠、会话时钟跳了 1 小时多，
而且 13:03 的定时任务起来和它并发）。我把它终止了，改用**定时任务那次**的干净测量值：
13:03:03 → 13:05:04。

**两个 crawl 并发写同一个 `notices.jsonl` 是真实风险**（都做原子替换，谁后写谁赢，
数据不会半份，但可能互相覆盖）。定时任务每 30 分钟一次，手工验证时**必须先看有没有在跑**。
这一条已经写进 journal，也建议后续给 crawl 加一个简单的进程锁（本轮没做，避免动到正在跑的定时任务）。

## 四、测试

`tests/test_fast_guard.py`（10 条断言）：

- 完整基线通过
- 文件不存在 → 拒绝，原因含"不存在"
- 空文件 → 拒绝
- **从中间截断** → 拒绝，原因含"损坏/换行"
- 只有 50 条 → 拒绝
- 真跑一次子进程：退出码非 0、**没有写出产物**、日志含"拒绝启动"

```
python tests\test_fast_guard.py → ✅ 全部通过
```
