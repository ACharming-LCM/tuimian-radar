### ① 合规：`review_status` 从公开字段里去掉

A 指出的原文：

> `rejected` 的语义是"被举报过但举报不成立"。一旦公开，
> **任何人都能看出哪些帖子被举报过** —— 举报这件事在匿名论坛里本身就是敏感信息。
> `VISIBLE_STATUSES` 只保证 hidden/pending 的帖子不出现，
> 但**可见帖子的状态仍然泄露了它被举报过**。

确认了契约：`contracts/api.md` 第 154 行列了九个公开字段，
**含 `report_count`、不含 `review_status`**；第 155 行明确写
`author_real_id` / `created_ip` / `review_status` **只在 `/api/admin/queue` 返回**。

所以从 `PUBLIC_POST_FIELDS` 里删掉 `review_status`。
`report_count` 是契约定的公开字段，**我不动它** —— A 的指示也只点了前者。

**C 的前端确实有一道防线**（`web/assets/forum.js:19`）：

```js
const FORBIDDEN_FIELDS = ['author_real_id', 'created_ip', 'review_status'];
```

他把 `review_status` 列进了禁字段表 —— **那是防线，不是误报**。
我改完之后他那个红框应该自己消失。

顺手把测试加强成**对着 fixture 比字段集合**（`posts.list.json` 正好九个键），
不再在测试里另抄一份字段表 —— 那就是同一张表的第三份拷贝，必然漂移。
另加一条用例 `可见帖也不泄漏被举报过这件事`：
举报一次（不到阈值，帖子仍可见）之后，前台列表里**不能有 `review_status`**。

### ② 演示冒烟：`server/tests/demo_rehearsal.py`

按 A 给的 5 步依次打**真实 HTTP 接口**，出这样一张表：

```
① 今日更新   ✓  counts.reparsed=21 changed=0 全部带 why
② 公告列表   ✓  前 5 条 relevance=[2,2,2,2,2]（首档 2 在打头） 字段 17 个
③ 背景匹配   ✓  30 条，score 降序 0.9205→0.4634，全部带 reasons
④ 生成套磁信  ✓  引文 5 条（body_text+deadline+materials+title），url 全部非空
⑤ 论坛发帖   ✓  举报 3 次后前台 1→0，后台可见实名+举报理由，无 token 401

结果：5/5 步通过（总耗时 1.8s）
```

**断言只绑结构和不变量，一个数字都没有**（A 特别强调的）：

| 断言 | 是不变量吗 |
|---|---|
| `relevance` 单调不增、同档内日期降序 | ✅ 排序契约 |
| `score` 降序、每条有 `reasons` | ✅ 匹配契约 |
| 每条引文 `url` 非空、`source` 是四个合法值之一 | ✅ 防编造机制 |
| **`body_text` 引文逐字能在该公告正文里找到** | ✅ 可回链 |
| 字段集合 == fixture 的键集合 | ✅ 形状契约 |
| 举报到阈值后前台条数**真的减 1** | ✅ 行为契约 |
| 无 token 访问审核队列 401 | ✅ 鉴权 |

而**不是** `total == 72`、`reparsed == 21` 这种 ——
这一晚已经因为"数据规模"这类假设栽过三次（额度状态、条数、页码），
数据变了脚本不该红。

**几处刻意的设计**：

- **自己起临时端口的实例**（`socket` 拿空闲端口），不碰你在跑的 8000；
- **状态隔离在临时目录**（`TUIMIAN_STATE`）—— 跑冒烟不会把测试帖子塞进
  `server/var/state.json` 弄脏演示环境。实测跑前跑后 state.json 的 sha256 一致；
- 套磁信那一步**不写死 notice_id**，而是挑"正文最长的第一条" —— 数据换了也跑得动；
- 失败时打「**★ 断在第 ⑤ 步「论坛发帖」：公开字段不对：['review_status']**」，
  而不只是红绿灯。

**验证它不是安慰剂**：故意往 `PUBLIC_POST_FIELDS` 里塞回 `review_status`，
第 ⑤ 步变红并准确指出差的是哪个字段；恢复后回到 5/5。
