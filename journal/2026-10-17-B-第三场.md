**③ 论坛 + 审核队列（第 6 步）**

`server/forum.py` + 六个端点。三条这条代码要守住的底线，都有测试盯着：

1. **绝不返回可识别身份的信息。** `author_real_id` / `created_ip` 只进存储，
   响应里一个都不出现 —— 用**白名单投影**（`PUBLIC_POST_FIELDS`）保证不可能漏。
2. **`pending` / `hidden` 的帖子绝不出现在列表里。** 举报够了必须真的下前台，
   否则审核队列就是装饰、删帖规则就是空话。
3. **`author_display` 由服务端确定性派生**（sha1 取模选词），不接受前端传值 ——
   前端传的话作者能伪装成别人；不确定性派生的话"匿名"会变成"查不到自己发过什么"。

**实测完整流程**（`POST` 发帖 → 举报 3 次 → 审核 → 恢复）：

```
发帖          HTTP 201  author_display=匿名·等通知的松鼠
身份泄漏检查   无 author_real_id / created_ip / reports        ← 正确
同一人再发     代号一致                                          ← 确定性派生生效
举报 1/2 次    review_status=visible  report_count=1/2
举报第 3 次    review_status=pending  →  前台 total 立刻从 4 变 3   ← 真的下线了
审核后台       无 token 401 / 错 token 401 / 正确 token 200
              队列里能看到每条举报理由 + 后台可见实名留痕 u_alice
审核动作       restore → rejected（前台可见，4 条）
              hide    → hidden（前台 3 条）
              delete  → deleted（前台 3 条）
```

### 卡住 / 踩到的

1. **`_quota` 塞进 body 把契约测试搞红了。** 我一开始把"今日剩余额度"放详情响应的
   body 里，`详情默认键集合与_fixture_一致` 立刻失败 —— 而那条测试是对的：
   fixture 就是一条原始记录、没有任何额外键。
   **额度是访问控制状态，不是公告数据**，混进 body 早晚有人误用。
   改成响应头 `X-Quota-Limit` / `X-Quota-Used` / `X-Quota-Remaining`，body 严格不变。
   这个坑值得记：**加了功能反而破坏了形状契约，而报警的是老测试。**
2. `StateStore(":memory:", None)` 我传了 `None` 当状态，炸了一堆。
   用 `StateStore.load(":memory:")`。
3. **PowerShell 做 JSON 请求体验证不可靠**：`-d '{\"title\":\"...\"}'` 里的
   转义在 PS 下会坏，`POST /api/posts` 报 422 让我以为接口有问题 ——
   其实接口好的，是请求没发对。用 Python 复核后 HTTP 201 正常。
   以后 curl 验 JSON 一律 `--data-binary "@文件"`，别在命令行里拼转义。
   （同一个坑第二次踩：`$pid` 还是 PowerShell 只读变量，改名。）
