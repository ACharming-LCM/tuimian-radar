## 二、五环逐条

### 环 1：坏行必须让门禁变红

**改了什么**

- `server/store.py` 新增 `load_health(meta)` —— 判据**只有这一处**，
  门禁和接口都调它，所以"接口说没事"和"门禁说没事"不可能分叉。
  三态：`ok` / `degraded`（有坏行被跳过）/ `empty`（0 条）。
  `degraded` 排在 `empty` 前判断：全是坏行时根因是"坏了"，不是"还没跑"。
- `load()` 的坏行记录加了 `excerpt`（原文片段），并区分
  "不是合法 JSON" / "顶层不是 JSON 对象" / "缺 id"——原来后两种都报"缺少 id 字段"，
  那是**把人带去查字段，而实际是整行形状就不对**。
- `/api/health` 的 `data` 下新增 `load_state` 和 `load`（含 `bad_lines[]` + 人话 message），
  **`skipped_lines` 保留**（老调用方读它，删掉是破坏兼容）。

**喂的坏输入**：`notices.jsonl` 第 6 行改成 `{ 这一行坏了`（复制到临时目录改的，真文件没动）。

**怎么响的**

```
loaded: 195  skipped: 1  state: degraded
bad_lines: [{"line": 6, "error": "不是合法 JSON：Expecting property name…", "excerpt": "{ 这一行坏了"}]
message: 196 行里有 1 行无法解析（第 6 行：…）—— 已跳过这 1 行，服务仍可用，
         但**少了 1 条公告**。要修的是数据源，不是接口
GET /api/health  → data.load_state="degraded"   data.skipped_lines=1
GET /api/notices → total=195   ← 能读到的照常给
```

**门禁**：`加载自检_坏行必须让门禁变红而且说清第几行` 两头都盯 ——
① 真数据必须 `state == "ok"`（磁盘上真出现坏行，这条立刻红，报出第几行什么错）；
② 造一个坏文件（第 2 行半截 / 第 4 行 `["我不是对象"]` / 第 6 行缺 id），
必须被认出来、行号对、`usable` 仍为 True、接口仍返回能读到的 3 条。
配套一条 `加载自检_正常数据不报假警`（对照组）。

**没做成反向错误**：**不拒绝启动**。文件不存在仍然 fail loud（`FileNotFoundError`）——
配错路径和"某一行坏了"是两回事，前者做什么都是错的。

### 环 2：`relevance` 接进默认排序 —— **这条的前提我核了，不成立**

**事实**：`server/store.py:_sort_key_publish_desc` **早就是**
`(relevance desc, publish_date desc)`，门禁里也有一条
`排序_publish_desc_是两级降序_relevance_再日期` 在跑（126 条里就有它）。
也就是说 D 实测到的"前 5 条里混着学院风采合集"**不是排序没接**，而是：

```
89 条 relevance=2 里，8 条是宣传页：
  学院风采合集：弘毅笃行…研究生招生宣传册        (rel=2)
  研究生招生直播宣讲会                          (rel=2)
  北京大学物理学院电子信息专业硕士招生简介        (rel=2)
  …（另有 4 条同型）
原因：relevance_of 的标题正向词里有"招生"，宣传册的标题里也有"招生"
```

**这是数据层的判据问题，不是接口层的排序问题**。排序只能做一件事：
同档内按日期。要改的是 `collector/fields.py:relevance_of`，
**那是 D 的目录，我没动**（在下面第四节写清了，留给他判断）。

**我做了什么**

1. 加了一条**造数据**的用例 `排序_relevance_高于日期_用造的数据验而不是赌磁盘`：
   四条记录，`rel=2/2026-01-05` 必须排在 `rel=0/2026-10-16` 前面，
   且 `rel=2` 里新日期在前（档内时效性），且 `rel=0` 那条**一条都不许消失**。
   **为什么必须造数据**：真数据上 `relevance` 和日期恰好同向，
   用真数据断言"高的在前"等于赌"今天的数据恰好长得像结论"。
2. 加了一条**结构性锁** `排序_relevance_不许混进列表载荷`：
   白名单没有它、默认响应每个 item 没有它、`?meta=1` 也没有。
3. 把 `LISTING_SORT_FIXTURE_STALE` 从 `True` 改成 **`False`**：
   D 已经重跑过 fixture，我核过**当前接口与 fixture 50/50 逐条逐字段完全一致**
   （`items == items` 为 True），所以这条比对现在**严格**了 —— 谁改排序立刻红。
   **不用再重跑 fixtures。**

### 环 3：套磁信引文 —— 这一类原来是纯 happy case

**实测（全量 196 条扫一遍，改之前）**：`body_text` 引文里有 **2 条表格行**，
它们是"整篇正文都是表格"时的兜底，带了警告但**警告没人读，能看见的只有表格行本身**。

**改了什么（`server/letter.py`）**

- **删掉表格兜底**（`_table_quotes`）。表格行**一条都不进 `citations`**，
  纯表格式公告改成只引标题/材料/截止日期 + 如实说"正文是表格式内容"。
- 新增 `quote_problem(quote, source)` 作为**唯一判据**：
  表格行 / 以省略号结尾（残缺）/ 正文 <20 字 / 标题 <6 字 → 不给。
  阈值只有一处，别在别处再写一套（两份阈值迟早漂移）。
- 丢掉的东西**结构化地**说出来：响应新增 `quotes_dropped: [{source, reason}]`，
  **只给 source+reason，不给原文**（把表格行搬回来等于换个字段名继续显示）。
  同时 `warnings` 里给一句人话。
- 修了一个**我自己这次引入的真 bug**：`warnings_for` 原来重新跑一遍
  `pick_requirement_quotes` 判断"有没有候选"，而引文之后又过了一道质检 →
  "候选有、但全被判不准丢了"的那批公告，信里一句正文都没引、**警告一个字不说**。
  现在它只吃 `citations` + `dropped`：**判据和结果必须是同一个东西**。

**喂的坏输入（造的三条）**

| 坏输入 | 结果 |
|---|---|
| 纯表格正文 | 引文 2 条（标题+截止日），**0 条表格行**；警告说"正文是表格式内容" |
| 残缺标题 `…通知…` + 截断句子 | 引文 **0 条**（宁可不给）；`quotes_dropped` 两条"残缺"；警告说"判不准" |
| 正文只有"报名材料"（4 字） | 正文引文 0 条；`quotes_dropped` 说"只有 4 个字" |

**正常公告不受影响**：另造一条正常公告，正文引文照常给、`quotes_dropped` 为空。
全量 196 条扫一遍：**坏引文 0 条**，引文逐字都能在原文里找到。

**一个我刻意没改的地方**：`materials` 里的单项（如「论文」「身份证」）**不加长度下限**。
它们是结构化字段、`label` 已标明"材料要求"，加下限会把"身份证""成绩单"一起砍掉。
「两个字」那个事故里，「论文」其实来自 `materials` —— 我的判断是保留，理由写进契约 §3 了。

### 环 4：状态与重启

**(a) 状态文件损坏 —— 原来是静默重建**

实测三种坏法，原来各错一处：

| 坏法 | 原来 | 现在 |
|---|---|---|
| 半截 JSON | 改名 + 空状态，**health 一个字不说** | 说清：备份到哪、**哪些没恢复** |
| 顶层是 `[]` | `AttributeError: 'list' object has no attribute 'setdefault'` —— **服务起不来** | 按损坏处理 |
| `users` 是字符串 | 服务起来了，**每个 `/api/me` 都 500** | 按损坏处理 |

现在：原文件**只改名不改不删**（`.broken-<时间戳>`，内容逐字节比对过）→
空状态继续 → `StateStore.recovery` + `/api/health` 的 `state.ok / state.recovery` 说清。
**不拒绝启动**（同一个取舍），但**审计没了这件事必须响**。

**(b) 并发写 —— 未复现，但结构上修了**

我压了 60 个并发写、10 线程抢免费额度：**没复现**（额度正好放行 3 条、帖子没丢）。
但代码原来确实不安全：`_lock` 只锁了 `json.dump`，而**改状态发生在锁外** ——
`RuntimeError: dictionary changed size during iteration`、以及"读-改-写"丢更新
（额度多放行一条、同一个人的两次举报算成两个人）。

**改法**：`RLock` + 公开的改状态方法都在锁里 + `with state.transaction():` 给
`forum.report_post` / `forum.moderate` / app 的两处申诉改状态用。
**门禁** `state_并发写不丢更新也不写坏文件` 守四条不变量：
被接受的写一条不少、文件始终合法 JSON、不留 `.tmp`、10 线程抢额度**正好 3 个 200**。
**靠运气通过不是修好，所以这条门禁守的是"别把锁拆掉"。**

**(c) 限速器不跨重启 —— 我选"写进契约"，没修**

理由：落一份时间戳进 `state.json` 会让它一直涨，而它防的是"短时间广撒网"，
重启清零对这个威胁几乎没损失。所以契约 §13.4 现在**写死**：
**演示期间不重启服务**。这是"写明并接受"的缺口，不是待办。
（真要跨重启，`state.py` 已经有串行化的写锁，加一次写盘即可。）

**审计 append-only**：没动（B 验过，结构上就没有修改/删除方法）。

### 环 5：空数据 / 首次运行

**改了什么**：`/api/notices?meta=1` 顶层新增 `data_state`：

```json
{"loaded": 0, "matched": 0, "skipped_lines": 0, "source_empty": true,
 "empty_reason": "source_empty",
 "note": "数据源里一条公告都没有（管道还没跑完/跑空了）—— 这不是‘你的筛选太窄’，是现在没有任何数据可展示"}
```

`empty_reason` ∈ `null`（有结果）/ `no_match`（筛太窄）/ `source_empty`（没数据）。
**只在 `meta=1` 里给**（默认形状被 fixture 钉死，先例 issues/004 的 `warnings`）。

`/api/health` 这边：`load_state == "empty"` + message 说"这不是筛选没命中，是数据还没进来"。

**门禁**：`空数据_必须和_筛选没命中_分得开`（三态全走一遍 + 对照"有结果时不给 empty_reason"
+ 默认形状不许变）、`空数据_筛选接口也不许崩`（0 条时每个列表接口都得 200、facets 空列表、
详情老实 404）。

**给 F 的接口口径（第 5 环要求跟 F 对齐）**：
列表页已经在用 `?meta=1`（`web/assets/notices.js`），直接读 `data_state.empty_reason`：
`source_empty` → 「**数据还没加载**」；`no_match` → 「没有符合条件的公告」。
**⛔ 不许把 `source_empty` 显示成"没有符合条件的公告"** —— 前者是系统的事，后者是用户的事。
