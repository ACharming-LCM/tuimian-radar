## 一、这一轮的核心判据变了

前面几轮的完成标志都是**正向**的（9 页都能开、5 步都能走、门禁全绿）。
那证明的是**正常路径通**。**它不是鲁棒性。**

鲁棒性的判据是反过来的，三个问题：

1. **坏的时候，是失败还是"看起来正常"？**（这个项目栽得最多的一类）
2. **失败了，说不说得清是什么坏了？**（"解析失败"四个字等于没写）
3. **下一次坏，还测不测得出来？**（一次性人工验证 ≠ 鲁棒性）

所以每一环都要求：**造一个坏的输入 → 断言结果是"响"而不是"静默降级"。**

## 二、我实测到的三个证据（不是猜测，两个已复现）

**① 后端静默丢数据（已复现）**

```
把 notices.jsonl 第 6 行改坏 → 服务加载 195 条（少了 1 条）
/api/health: "loaded": 195, "skipped_lines": 1
门禁：126 通过 / 0 失败
```

`skipped_lines` 是**记下来了**（B 这点做对了，不是黑盒），
但**没有任何东西会因为它变红**。少一条公告，所有门禁全绿。

**② 后端默认排序还没接 `relevance`（已复现）**

```
/api/notices?size=5 前 5 条：
  2026-10-16 大连理工  关于中国教育国际交流协会邀请…
  2026-10-16 华中师范  学院风采合集：弘毅笃行…
  2026-10-14 电子科大  001信息与通信工程学院
  2026-10-14 电子科大  研究生招生直播宣讲会
  2026-10-14 电子科大  接收2027年优秀应届本科毕业生免试攻读…
```

第 2 条是「学院风采合集」。`relevance` 这个字段我这边一直给着，没被用上。

**③ 前端要面对的畸形载荷（已确认形状差异）**

```
fixtures/notices.detail.json  有 field_state（4 个键齐全）
fixtures/notices.list.json    没有 field_state（白名单挡掉了，这是对的）
```

也就是说前端**必须能处理"详情有、列表没有"**这件事，而不是假设它到处都在。

## 三、我自己这块（D）接下来做什么

**先启日更稳定性** —— 它不是"再加个功能"，是**唯一能把"每天更新"从承诺变成事实**的事，
而且需要连续几天才能出数，越晚启越吃亏。

1. 每日运行包装 `tools/run_daily.py` 追加一行到 `data/out/stability.jsonl`
   （日期 / 条数 / 用时 / 各站点成功失败 / 与上一天的差值）
2. **连续跑两次**，断言第二次不是"全部新增"（幂等性 —— 现在是没人验过的）
3. 数据层鲁棒性，我这边要补的：
   - **缓存被截断时会不会把半截正文当完整证据**（我刚试了整文件截断 → 安全落到
     `missing`；但**截在正文容器内部**、剩余仍 ≥150 字时会怎样，还没验）
   - `notices.jsonl` 写一半崩掉 → 下次跑会不会读进半条
   - 同一轮里某几个站点全挂 → 会不会把 196 条覆盖成 100 条（写盘前有没有闸）
4. 欠账：`history/index.json` 的 `days[]` 补 `reparsed` 列（E 那边第 5 次提）

## 四、调度纪律（沿用 COLLAB，不新造）

- **各自只改自己目录**。任务书里凡是要求改别人文件的，一律写"提 issues 或让对方改"。
- **做完写 journal**，格式照旧（做了 / 怎么验的 / 卡在哪 / 契约动没动）。
- **契约改动先记 `CHANGELOG.md`**，破坏兼容的要在 journal 里 @ 所有人。
- **别串一条不可回退的长链**：一环做完自己验完再下一环，用户会随时打断。
- **不许用 subagent 做验证**（实测 83 个代理吃掉 357 万 token，且失败会被伪装成结论）。
  核验一律主 agent 内联：Grep → Read → 比对。

## 五、两边共同的验收底线

不管做哪一环，收工时这三条必须能答出来：

1. **我这一环，坏输入长什么样？我让它怎么响了？**（有测试/有日志/有界面提示）
2. **这个"响"会不会误伤正常情况？**（宁可漏报一次，也不要每次都报警 ——
   每次都报警等于没有报警）
3. **下一个人接手，怎么在 5 分钟内复现我说的那个"响"？**（一条命令或一个路径）
