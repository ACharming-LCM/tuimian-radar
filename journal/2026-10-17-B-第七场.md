### ① 两条脆测试（A 说得对：这么写，数据一变就红一次）

**`json_是_utf8_且中文不转义`** —— 我原来断言 `"浙江大学" in r.text`。
那等于把"编码正确"寄存在"浙大今天还在第一条"上。A 删掉浙大那个整块是科研的栏目、
第一条变成南开，它就红了，而"中文没被转义"这件事一点没变。

改成通用断言，查**原始字节**：

```python
raw = r.content                        # 不过任何解码
assert b"\\u" not in raw                # 没有 \uXXXX 转义
assert any(0xE4 <= b <= 0xE9 for b in raw)   # 确实有 UTF-8 三字节中文
text = raw.decode("utf-8")
assert any("\u4e00" <= ch <= "\u9fff" for ch in text)   # 解出来真是中文
```

**`changes_空报告也要给完整结构`** —— 我那条文档字符串自己写着"当前磁盘上就是空报告"，
**那是把断言绑在一份每天都会被重写的文件上，只有恰好没变化的那天才绿。**
改成自己造一份空报告注入（`_changes_client(...)`），完全不碰磁盘。

顺手把同一毛病的老测试也改了 —— **`changes_磁盘上的真实文件走一遍投影`**，
它原来断言磁盘文件的 counts 键集合是固定七个，`reparsed` 一加就红。

这是任何一天都必须成立的，跟文件里当天有什么内容无关。

**这两条是同一类错误的两个样本：把"某一天的数据长什么样"写成了断言。
门禁必须可重复 —— 一个会随数据变红的门禁比没有门禁更坏。**

### ② `reparsed` 透传（纯新增）

顺手把 `changed` 和 `reparsed` 的投影抽成同一个 `_project_changed_like()` ——
**形状完全一样，但语义完全不同，绝不能合并：**

| 桶 | 含义 | 判据 |
|---|---|---|
| `changed` | **学校真的改了通知** | 正文哈希变了 / 附件清单变了 |
| `reparsed` | **我们改了抽取代码** | 正文和附件都没变，只有抽取字段不同 |

契约 api.md 第 431 行讲的正是这个：A 修好标题解析器之后，日报立刻报出「有变化 22 条」，
而**公告一个字都没变** —— 用户会以为学校改了 22 份通知。
这跟 `reidentified` 是同一类错误：**把"我们的处理变了"说成"外面的世界变了"。**

加了一条专门的用例 `changes_reparsed_必须和_changed_分开` 守它。

活接口实测：

```
counts: {'previous': 78, 'current': 72, 'added': 0, 'changed': 0,
         'reparsed': 6, 'removed': 6, 'reidentified': 0, 'unchanged': 66}
reparsed 6 条，带 body_text 吗: False
  fields={"title": ["南开大学2026", "南开大学2026-2027学年第一学期申请答辩学术博士平台评审名单"],
          "target_year": [2026, 2027]}
  body_changed=False     ← 正文确实没变，符合 reparsed 的定义
```

### ③ `/api/health` 的乱码 —— **不是显示问题，是真 bug**

A 说"小问题，但评委真去看健康检查就会看到"。查下去发现**根因在我**：

```
/api/health  Content-Type: application/json              ← 没有 charset！
/api/notices Content-Type: application/json; charset=utf-8
/api/me      Content-Type: application/json; charset=utf-8
```

**按 HTTP 规范，`application/json` 不带 charset 时默认按 Latin-1 解。**
守规范的客户端就会把"文档"读成 `ææ¡£` —— A 看到的正是这个。

原因：`/api/health` 是**唯一一个直接 `return {...}`**（没走我的 `_json()` 包装）
的端点。`/api/facets` 也漏了。两个都改成走 `_json()`。

**为什么会漏**：我的 `_json()` 里明明写了 `charset=utf-8`，但"记得用它"靠的是自觉。
所以我加了一条**遍历所有路由**的测试 —— 任何返回 JSON 的接口，Content-Type 里
必须有 `charset=utf-8`。抽查会漏（我这次就是漏了两个），遍历不会。

**并且验过这条测试不是安慰剂**：用一个"直接返回 dict"的 `_json` 替身模拟修复前状态，
它确实变红了（`FAIL 每个接口都带_charset_utf8`，84 条里 14 条失败），
恢复后回到 84/84。

修复后全部 10 个接口：

```
/api/health     application/json; charset=utf-8  ok
/api/facets     application/json; charset=utf-8  ok
（其余 8 个同样 ok）
demo_auth.note: D3 演示用假鉴权，不是权限系统，别拿它当安全边界
state.note    : 服务端运行时状态（帖子/订阅/额度），不在 data/out/ 下
```
