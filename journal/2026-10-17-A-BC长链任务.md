# 给 B：**订阅与提醒链路**（产品真正要卖的那个东西）

现在 `/api/changes` 只是"这轮变了什么"。而用户付费买的是
**"跟我有关的、变了的东西"** —— 这两者差着一整条链路。
这条链有 6 环，按顺序做，每环做完自测再下一环。

### 第 1 环：先写契约（`contracts/api.md` 新增一节「关注与提醒」）

想清楚再写代码。至少要定：

- `POST /api/watch` —— 关注什么。粒度至少到**学校**和**院系**，
  再加一个**关键词**（用户可能只关心"夏令营"）。同一用户重复关注要幂等。
- `GET /api/watch` —— 列出自己的关注。
- `DELETE /api/watch/{id}` —— 取关。**取关不存在的 id 要返回什么**也要定。
- `GET /api/digest?since=YYYY-MM-DD` —— **核心**。返回"该看什么"：
  · 按关注规则过滤 `changes.json` 的 `added` / `changed`
  · **`reparsed` 绝不能进提醒**（那是我们改了代码，不是学校改了通知）——
    这条是我们踩过坑立下的规矩，提醒里混进它就等于天天骗用户
  · 每条要带"为什么提醒我"（命中了哪条关注规则）
- 空关注、关注了但本轮无变化、`since` 早于我们有记录的时间 —— 三种边界都写下预期

### 第 2 环：实现 `/api/watch`

- 按 `user_id` 存（沿用现有假鉴权那套，别新造一套）
- 幂等、可删、能列
- 落盘格式要和 `server/var/` 现有那套一致

### 第 3 环：实现 `/api/digest`

- **它读的是 `changes.json`，不是公告库** —— 提醒是关于"变化"的
- 每条提醒必须能顺着 `notice_id` 点进详情页
- **`reparsed` 单独一栏或干脆不提**，你想清楚哪个对用户更好，写进契约

### 第 4 环：端到端测试（**这一环最容易偷懒，别偷懒**）

必须覆盖这几种，而且**不许依赖磁盘上恰好是什么数据**：

1. 没关注任何东西 → digest 返回空，且结构完整（键一个不少）
2. 关注了一个**这轮没变**的院系 → 空
3. 关注了一个**这轮有新增**的院系 → 命中，且能点进详情
4. 关注的关键词命中一条 `changed` → 命中
5. **`reparsed` 一条都不出现**（这条是回归用例，防我们以后改坏）
6. 取关之后再查 → 不命中
7. 重复关注同一条 → 只有一条

### 第 5 环：`/api/changes/history` 和 digest 对齐

历史里多天，digest 要能跨天。**口径必须一致**，不然"过去 7 天变了什么"和
"今天的 digest"会互相打脸。

### 第 6 环：顺手把门禁里那两条红灯修掉

`faculty_group_kind_可筛选` / `faculty_group_kind_每条都有值且与参考实现一致`。
**改法是循环取全再断言，不是把 50 改成 100。**
（我导师数据从 67 涨到 259，硬编码页数的假设还会再破。）

**这一环的真正目标不是修两条测试，是把「假设数据能塞进几页」这个写法清干净。**
你可以在 `run.py` 里加一个小工具函数 `fetch_all(path, params)`，
把所有分页取数的地方都换成它 —— 这一步做完，这类红灯以后不会再出现。

### 完成的标志

- `contracts/api.md` 有新一节，边界都写了预期
- 7 条端到端用例全绿
- 门禁全绿
- `server/var/` 里能看到关注数据落盘
- **你要能一句话说清"用户为什么会为这个付钱"**

# 给 C：**前端在四种状态下都要站得住**

现在的页面都是在"数据充足、接口 200"这一种状态下验的。
演示只要网络一抖、或者某个院系没抓到数据，就可能露出没处理的样子。
这条链 5 环，**全部自己造条件验，不用等别人**。

### 第 1 环：四种状态 × 每个页面

对 9 个页面，逐个造出这四种情况并截图：

| 状态 | 怎么造 |
|---|---|
| 正常 | 现在这样 |
| **空数据** | `?api=fixtures` 配一个空 items 的样例（自己造，别改契约文件） |
| **接口 500** | 临时把 base url 指到一个会 500 的本地桩 |
| **接口超时** | 指向一个只 sleep 不返回的本地桩 |

**每一格都要有明确表现**：不能白屏、不能 `undefined`、不能一直转圈没有出路。
特别是**空态**：0 条公告 / 0 个导师 / 0 条帖子时要有一句人话，而不是一片空白。

> 这一环产出一张矩阵表（9 页 × 4 态），空格里写"看到什么"或"✓"。
> 你上一轮就是靠截图自查抓到自己的 bug 的，继续用那个办法。

### 第 2 环：把"前台字段自检"扩成**契约一致性面板**

你那块自检红框抓出过 `review_status` 泄漏 —— 那是个好防线，值得做厚：

- 逐个页面比对 `contracts/api.md` 里的字段白名单
- 页面上**渲染了但契约里没有的字段** → 报警
- **契约里有但页面从没用到的字段** → 也列出来（可能是我们漏做了，也可能是废字段）
- 面板要能一键打开，最好带一个"复制报告"按钮，方便贴进 journal

### 第 3 环：投屏分辨率

演示是**投屏**的，你只验过 1440×2200。补 **1920×1080**（最常见投影仪）：

- 首屏 3 秒内能不能看懂"这是什么网站"
- 有没有需要横向滚动的地方
- 字号在 3 米外看不看得清（宁可大一点）

### 第 4 环：`docs/USER-TEST.md`（还欠着的那件）

任务脚本 + 观察记录表 + **先写下来什么算失败**（判据我上一条给了）。
不用等人来测就能先写。

### 第 5 环：把以上 4 环写成一页 `docs/FRONTEND-STATE.md`

- 9×4 矩阵表
- 发现的问题 + 改没改 + 为什么
- **没改的要写明理由**（有些可能不值得改）

### 完成的标志

- 9×4 矩阵没有空格
- 契约一致性面板能跑，且**至少再抓到 1 个真问题**
- 1920×1080 下 9 个页面都能看
- `docs/USER-TEST.md` 和 `docs/FRONTEND-STATE.md` 都在
- 改完再截一次图自查（**"我改好了"和"屏幕上对了"是两件事**）
