> 交办：B12（suppressed 瘦身）+ B13（library / health 提速）+ 一条纪律（性能进门禁）。

## 二、B13：两个次慢的

**`/api/library` 608 ms → 39 ms**：不是返回了全量 body（只有 14.2 KB），
是它对**每条事件**调一次 `live_store.get()`，而 `get()` 每次都全表扫描。

**`/api/health/data` 218 ms → 7 ms**：它每次把 10 MB 的 `notices.jsonl` 解析一遍。
两处修：
1. 接口层把**已加载在内存里**的记录传进去（`notice_records` / `event_records` 注入点）；
2. 加 3 秒 TTL 缓存（**只对真实路径 + 真实时钟生效**，门禁注入的调用每次真算，
   否则时间相关的断言会被上次结果污染）。

## 三、真正的根因：`store.get()` 是 O(n²)

```python
# 改前
same = [r for r in self.records if r.get("id") == notice_id]
```

`/api/push/preview` 对**每一条事件**都调它：**2759 × 2751 ≈ 760 万次比较**。
数据 1135 条时只要 100 ms 上下，**完全看不出来**；到 2751 条就变成演示白屏。

改成一次性建 `id -> [记录]` 索引（`NoticeStore._id_index()`），之后 O(1)。
`records` 在 load 之后不再变（LiveStore 重载会换新实例，索引跟着重建），所以不需要失效逻辑。

**这个修法同时救了 `/api/library`、`/api/push/preview` 和所有走 `get()` 的地方** ——
一处 O(n²)，四处受害。

## 四、纪律：性能进门禁

新增两条（契约 §22）：

- `perf_推送预览体积不超过六十KB`：< 60 KB，且必须带 `suppressed_total` / `suppressed_tally`
  （**少了计数出口就不是"可解释"，是"看不见"**）。
- `perf_首屏接口在真实数据下不超过三百毫秒`：`push/preview` / `library` / `updates` /
  `notices` < 300 ms，`health/data` < **100 ms**（挂在页头上）。

耗时取**三次里的最小值**：机器负载会抖，取 min 才是"这段代码要多久"，
取 max 会变成"刚才那台机器有多忙"。

**反向验证**：把 `store.get()` 改回全表扫描 → `perf_首屏接口…` 立刻红（194/1）；
还原 → **195/0**。这条断言盯着的是"**没有随数据规模变差的东西**"，
不是"这台机器上是 100 ms"。

## 六、风险

| 风险 | 说明 |
|---|---|
| 性能断言依赖机器 | 取三次最小值 + 上限放宽到 300 ms（实测 100 ms），有 3 倍余量 |
| `health/data` 有 3 秒缓存 | 页头显示的数据年龄可能滞后 ≤3 秒；需求上可接受，已写进契约 |
| `suppressed` 只给样例 | 靠 `suppressed_truncated` + `suppressed_total` 说明，不会静默截断 |
