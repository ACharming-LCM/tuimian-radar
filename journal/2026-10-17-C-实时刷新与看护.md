### ① 看护做完了，而且它判的不是"进程在不在"

`_f-watch.py`（仓库外）。**它不是进程守护，是数据新鲜度守护。**

为什么分开想：uvicorn 活着不等于数据在更新。最危险的坏法不是宕机，
是**服务好好的、数据停在 10 月 17 日** —— 页面上一切正常，但那句"每天更新"是假的。

四档判据（顺序即优先级）：

| 结论 | 什么情况 | 该重起吗 |
|---|---|---|
| `OK` | 端口在、health 200、数据还新 | 否 |
| `RESTART` | 端口没了 / health 不 200 / `loaded=0` / **调度器死了** | **是** |
| `FETCH_BAD` | 调度器活着也跑了，但 run 是 failed（TLS/上游改版） | **否** |
| `STALE` | 没坏但旧了（数据龄 > 阈值） | **否** |

**最关键的一条：`FETCH_BAD` 不判重起。** 抓取本身失败，重起一百次还是 failed ——
那种要修抓取。这是"看到旧了就重启"会犯的典型错误：把真问题变成"服务在重启"的假象。

**调度器死没死怎么判**（这一层是这次才想清楚的）：
抓取的定时器是 uvicorn 里的一个 daemon 线程（`app.py:1203`），**进程死 = 定时器死**。
所以看护本质上是在保数据新鲜度的发动机。判据是"最近一次留痕离现在多久"——
正常最长沉默 = 节拍(24h) + 首次延迟(5min)，超了就是死了。

而且 `crawl.py:316` 那句注释说得对：**判断依据永远是数据本身，不是计时器**。
所以重启不丢判断 —— 实测：我重起 8001 之后 5 分钟，调度器自己跑了一轮，
判「5.2 小时前，还没到节拍」→ 跳过。没抓，也没白抓。

**自检 `_f-watch-selftest.py`：7 种形态造出来跑，7/7 通过。**
（healthy / service_down / loaded_zero / sched_dead / sched_silent / fetch_failed / plain_stale）
真实环境里这些坏法代价太高（改数据、停服务、等 24 小时），所以用 mock 在同一个进程里造。

**默认不自动重起**（`--restart` 才开）。理由：这个环境里可能同时有别的 agent 在清进程，
没搞清楚"上次是被人杀的还是自己僵住的"就自动重起，可能是在跟人打架。
先让它只报告，但它会把**该不该重起**判出来。

### ② 实时刷新做完了（`web/assets/live.js`，已提交 8ba5a2a）

**独立文件，一行没碰 `common.js` / `style.css`** —— 因为别的 agent 正在改那两个文件。

这个功能里的"实时"是什么、不是什么，写在 `docs/LIVE.md` 第 1 节：
- **是**：那行「数据更新于 N 分钟前」自己走（每 15 秒）；后台真更新了 30 秒内主动告诉你
- **不是**：把抓取提到分钟级。公告不是股票，一天一轮是常态

两个刻意的克制：
- **数据变了不自动替换列表** —— 用户可能正在读某条、正在筛选，内容自己跳变会失去位置感
- **时间推算用「取到的时刻 + 后端给的 age」**，不是 `now - generated_at` ——
  演示机时钟差几分钟就会显示"数据来自未来"，负数比不刷新更难解释

实测：时间 5h→6h 真的走了；伪造更新后提示条出现；真实轮询间隔 **29 秒**；三页（含 375）加载正常无溢出。

### ④ 8001 这一小时内掉了三次

不是代码问题（每次都是 200/402，日志无异常），是**多个 agent 在抢同一个端口/互相清进程**：

```
14:20 左右  掉（进程在、不监听）
14:32:50    另一个 agent 起了自己的 8001，把我的挤掉
14:40 左右  又掉（它起的那个也没了）
```

**这件事本身就证明了看护的必要性** —— 但它也说明：**自动重起会在多人环境里打架**。
所以我建议的用法是：看护只报告，人在看到 `RESTART` 之后自己决定要不要动。

演示当天的正确做法不是靠看护，是：**别让别的 agent 动这个进程**。
