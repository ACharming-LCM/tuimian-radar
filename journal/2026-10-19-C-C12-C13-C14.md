## 二、三项的落点与判据

### C12 订阅（院校 + 学院）

| 判据 | 怎么验的 |
|---|---|
| 能关注任意组合并持久化 | `POST /api/watch` 后**重启服务**，`GET /api/watch` 仍返回同一批（落 `server/var/state.json`） |
| 订阅页能看全部、能取消 | `c12-subs-with-watches`：`summary`「关注 1 条规则 · 覆盖 1 所学校」，1 个开关 1 个取消按钮；DELETE 后重拉 |
| 375 不溢出 | `m375-subs-form`：`overflow=0`，输入框 44px、开关 label 46×44、取消 78×44 |

入口做了两处：新页 `subscriptions.html`，以及**详情页「下一步」里的「关注这个学院」**。
详情页那个按钮会先问服务端：已有同校同院的规则 → 灰绿「✓ 已关注这个学院」；
只有同校规则 → 「✓ 已关注 北京大学（整校）」；读不到 → **明说读不到**，
不默认成"未关注"（默认成未关注会让人重复点、以为关注失灵）。

**提醒开关只能放本机**：`/api/watch` 没有 `enabled` 字段（server 是 A/B 的地盘）。
所以开关存 localStorage（键带 user），页面上把范围写死：「只在这台浏览器上有效，
服务端不知道，也不影响它的每日推送口径」。这条已经记进 §五 转给别人。

### C13 站内通知中心

两个数据源，各管一半，**缺一半就会漏**：

1. `/api/digest?user=` —— 服务端按我的 watches 算好的「变了的东西」。
   匹配语义就是 `/api/notices` 那套 `substring_hit`，权威。
2. `/api/updates?days=7` ∩ 我的 watches —— 「最近新发布、还新鲜」的公告。
   这一半必须在**前端**匹配，因为 `/api/updates` 没有 `user` 参数。
   代价写在文件头：`/api/updates` 的 item 不带 `body_text`，所以关键词只搜
   标题/学校/院系/专业/标签，比服务端 `watch._hay()` 少一块正文 —— 宁可少报。

为什么不能只用 `/api/digest`：它只读变更记录，**没有变更的日子它是空的**
（今天就是这样：`empty_reason=no_changes_in_range`，但「今日更新」有 27 条）。
为什么不能只用 updates：一是关键词缺正文，二是"公告被改过"这类事只有 digest 有。

实测（干净身份，三次独立）：

| 场景 | 结果 |
|---|---|
| 关注南开，有更新 | 红点 **28**，面板 28 条，28 条带未读标记；`why`「你关注了 南开大学」，`when`「新收录 · 2 天前」 |
| 点「全部已读」 | 红点消失，`tuimian_read_u_c13_b` 里 28 个键；**刷新后仍是灭的**（`unreadMarks=0`） |
| 关注一个不存在的学院 | **不亮**；面板「关注了 1 条规则，最近没有新公告。（盯着最近 7 天的数据看过了）」 |
| 点通知 | `href=/detail.html?id=u50d849a2-7809-582802`（真公告 id） |

**一个修正**：第一版把 digest/updates 的失败 `.catch(()=>null)` 吞掉，
于是"两路都挂了"会显示成「最近没有新公告」—— 把"没读到"说成"没有"，
正是这个项目一路在防的错。现在任何一路失败都写「有一部分没读到：变更记录/今日更新（原因）」
+ 重试，并且**不许说"没有新东西"**。

### C14 剩余天数（四种状态）

`deadline.js` 是全站唯一的截止日措辞实现，所以只改一处，`匹配结果 / 公告列表 / 详情 / 推送`
四页一起变。四种状态（`c14-*` 四个实测）：

| 场景 | 屏幕上的字 | class |
|---|---|---|
| 还剩 5 天 | `还剩 5 天（10-24 截止）` | `dl-found dl-soon`（琥珀） |
| 还剩 1 天 | `还剩 1 天（10-20 截止）` | `dl-found dl-urgent`（红） |
| 已过期 | `已于 04-09 截止` + 「已过期」徽标 | `dl-found is-expired` |
| absent | `该公告未公布截止日` | `dl-absent` |
| unknown | `⚠ 未能读取截止日，请点原文核对 看原文 ↗` | `dl-unknown` |
| 跨年 | `还剩 80 天（2027-01-07 截止）` | 跨年写全年份 |

**天数怎么来的**：只有推送项带服务端算好的 `days_left`，`/api/notices`、`/api/match`
都没有。所以前端用 `Date.UTC` 把两个"日历日"规约到 UTC 零点相减，
**不做时区换算**（`new Date('2026-10-25')` 按 UTC 解析，东八区差 8 小时，跨日差一天）。
已知口径差：服务端用服务器日历日、这里是本机日历日，同一台机器相同，跨时区可能差一天。
**根治办法是让 `/api/notices`、`/api/match` 透传 `days_left`**，已记进 §五。

详情页另加了「下一步」三件事：核对原文 / 关注这个学院 / 看同一学院的其它公告，
第一句随截止日状态改口（还剩 N 天 / 今天截止 / 已截止 / 没公布 / 没读到）。

## 三、首屏：通知不进第一屏

`notify.js` 一装上就是每页 3 个请求（watch / digest / updates）。
第一版只在 `requestIdleCallback` 里发，实测**没用**：load 之后 idle 立刻就到，
三个请求和 `/api/push/preview` 撞在同一帧（心跳从 ~200ms 拖到 285ms）。

改成**硬等 1.2 秒**再走 idle。为确认这不是自我安慰，给量具加了 `BLOCK=notify`
（用 CDP 拦掉 `assets/notify.js`）做 A/B，同一页同一份数据各跑 5 次，量 `hb` 中位：

| | 中位 |
|---|---|
| 带铃铛 | 394 ms |
| 拦掉铃铛 | 455 ms |

**噪声比差异大**（单次 300~680 都有），所以结论只能下到"不构成可测影响"，
不能下到"快了 60ms"。判据看的是"第一张卡"，那条在 3 次复测里是 **316 / 343 / 233 ms（中位 316）**。
