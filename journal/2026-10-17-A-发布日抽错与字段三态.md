## 12:40 A（数据）— 截止日那个「30%」是错的；真正的问题在发布日

### 先说我自己的结论怎么被推翻的

任务本来是"把截止日填充率从 31% 提上去"。**我先量了一遍,发现这个分母是错的。**

```
未抽到截止日的 136 条：
  精确正则命中（真漏抽的强候选）   9     ← 而且这 9 条里大多数根本不是招生
  完全没有截止日表述            127
```

那 127 条是宣传册、团队风采、拟录取名单、讲座公告、考试安排 —— **它们本来就没有截止日**。
`null` 是对的，不是失败。

**所以"截止日 31%"这个数一直误导人**：它把"公告里没有"和"我们没抽到"混成一个数。
真要报，该报的是"**在有截止日的公告里，我们抽到了多少**"。

而查那 9 条候选时，翻出了一个**比截止日严重得多的问题**。

### 真问题：`publish_date` 抽错了

南开那条「关于延长我校第二批次申请-考核制博士报名截止时间」：

```
页面真实发布日  2026-04-13   （URL 是 /2026/0413/，页面上也写着「发布时间：2026-04-13」）
我们存的值      2026-05-14   ← 正文里「材料审核结果发布时间：2026年5月14日前」
```

根因在 `detail.py`：

```python
m = re.search(r"发布时间[：:]\s*(\d{4}[-/.]…)", head)
publish = common.iso_date(m.group(1)) if m else common.iso_date(head)
                                              ↑ 没匹配到就在整块 head 里抓"第一个像日期的"
```

`HEAD_XP` 在某些模板上会框进正文，于是**正文里的日期被当成了发布日**。

**为什么这比截止日严重**：`publish_date` 既是排序键又是展示字段 ——
等于给用户看了一个错的日期。**而且它反向害了截止日**：截止日要求 ≥ 发布日，
发布日被推后 31 天，正文里 2026-04-28 的报名截止就被那条噪声闸**正确地**拒掉了。
**一个错字段把另一个正确字段拖下水，报出来却像"截止日抽不到"。**
改对发布日之后，那条的截止日立刻出来了（`deadline=2026-04-28`）。

### 修的过程：先量再改，而且量错了两次

**第一次测量就是错的**：我只比 `detail` 单干的结果，而真实记录是
`detail 的日期 or 列表页的日期`，于是报出"99 条丢失日期"这种吓人的假象。

**改用 URL 内嵌日期当基准**（维普系 URL 就是 `/YYYY/MMDD/` —— 数据自带基准，
这种机会不多，遇到就该用）：

| | 正确 | 准确率 |
|---|---|---|
| 旧逻辑 | 46/52 | 88.5% |
| 第一次修完 | 49/52 | 94.2% |
| **最终** | **51/52** | **98.1%** |

**第一次修的时候我自己又踩了一个**：把正则放宽成裸 `时间[：:]`，
结果匹配上「**截止**时间：2026年4月28日」—— 把报名截止日当成了发布日。
**放宽一个正则时要顺手问一句：它还能匹配到哪些我不想要的东西。**

最终优先级：**页面标签 → URL 内嵌日期 → 正文前 400 字的标签**。
唯一那 1 条"不一致"（浙大 MSE）其实是**解析器对的**：URL 写 `/2026/1011/`，
页面自己写 `发布时间：2026-10-10` —— 页面标注更权威，而规则正是"标注优先"。

### 钉死它的三样东西

1. `test_detail.py` 加 3 条用例（head 无标签时不乱抓 / **「截止时间」不能当发布日** /
   页面标签优先于 URL）。假 HTML 的 class 一开始和真实选择器对不上、返回 `no_body`，
   换成 `infobox` / `arti_info` / `wp_articlecontent` 才对。
2. 数据门禁加不变量「发布日与 URL 内嵌日期一致 51/52」。
   **不做硬断言、只做 >5% 告警** —— 因为那 1 条是正常的（页面标注优先）。
   **反向验证过**：故意改坏 6 条 → 告警响；还原 → 0 失败。
3. 不改契约（`publish_date` 仍是 `string`），所以 B/C 都不用动。

# 给 B 的第四条链：**字段可信度 —— 值 / null / unknown 三态**

这条和我这一轮直接咬合，是我做的事的另一半，所以先由我给出接口。

## 为什么值得做

现在 `deadline: null` 一个值**同时表示两件完全不同的事**：

- 「**这公告里就没有截止日**」（我读了全文，确实没有）→ 用户该放心
- 「**我们没读到**」（正文没抓到 / 是扫描件 / 页面是 JS 空壳）→ 用户**必须自己去看原文**

**对用户这是天差地别的两句话，现在接口分不出来。**
评审问"这个还能报吗"，如果答成"没有截止日"，而实际上是**我们没读到**，
那是最伤信任的一种错 —— 比直接说"不知道"差得多。

## 第 0 环：我给你的形状（**我下一轮产出，你先按这个写**）

`notices.jsonl` 每条会多一个 `field_state`：

```json
"field_state": {
  "deadline":     "found" | "absent" | "unknown",
  "majors":       "found" | "absent" | "unknown",
  "attachments":  "found" | "absent" | "unknown",
  "body":         "ok" | "generic" | "missing"
}
```

语义（**要写进契约，别只写在代码注释里**）：

- `found` —— 抽到了值
- `absent` —— **正文读到了、内容足够，里面确实没有**
- `unknown` —— **我们判不了**（正文是兜底抽取的、太短、是扫描件、页面是空壳）
- `body` 单独一档：`ok`=用站点选择器取到了真正文；`generic`=兜底；`missing`=没取到

**我下一轮把它产出来。在你拿到真字段之前，用你自己造的样例测，别等。**
