## 13:40 B（后端）— 第十一场：订阅与提醒链路（六环）

**完成的标志**：契约写了边界 / 13 条全绿 / 门禁 102 全绿 / 一句话说清为什么付费。

那句话是：**`/api/changes` 说"这一轮变了什么"（所有人的、同一份）；
`/api/digest` 说"和我有关的变了什么"。没有关注，日报每天长得一样，用户看两天就不再打开；
有了关注，每天的结果都是他没见过的，而"错过一条"有真实代价（截止日、材料要求）。**

### ① 契约：`api.md` 新增第 11 节「关注与提醒」

写了 `POST/GET/DELETE /api/watch` + `GET /api/digest`，以及
**四种空结果各自的确定预期**。CHANGELOG 记了（纯新增、非破坏性）。

设计上有一个点值得单说：**`digest` 只发 `added` / `changed`**，
`reparsed` / `reidentified` / `removed` 一条都不出现。
理由**直接复用 §10 已经建立的区分** —— 只有前两个是"外面的世界变了"，
后三个是"我们的处理变了"。这不是我新定的规矩，是 A 那一节已经想清楚的事，
我只是把它用在提醒上。

> 把 `reparsed` 发进提醒 = 告诉用户"浙江大学物理学院有更新"，点进去公告一个字没变
> （是我们改了表格解析）。**提醒只要开始说谎，就没有人再看它**，
> 而"哪条被悄悄改了"正是我们收钱的功能。

`id` 由规则内容确定性派生（`w_` + 归一化规则的 sha1 前 12 位），
所以**幂等是自然结果而不是额外判断**：同一条规则重复 POST 必然同一个 id。
归一化把 `" 浙江大学 "`、关键词顺序不同、重复关键词都归成同一条。

**匹配语义和列表页共用同一个函数**（`store.substring_hit`），
不是复制一份过去 —— 复制出来的两份迟早漂移，而漂移的表现是
"我在列表页筛到了，关注了却收不到提醒"，用户会认为提醒功能是坏的。
契约里承诺的"两套语义一致"因此是**结构性成立**的，不是靠自觉。

**关键词的搜索面比 `/api/notices?q=` 宽一点**（标题+院系+专业+标签+正文），
这是刻意的：那边的"搜"是"我现在想找什么"，搜不到就换词；
这边是"以后出现这类东西请告诉我"，**漏掉的代价远大于多报的代价**。

### ④ 端到端测试：13 条（要求的 7 条 + 边界/对齐 6 条）

要求的 7 条全部落地，另加契约里承诺的边界。**一条都不读磁盘** ——
磁盘上现在恰好是 `added=0 / changed=0`，依赖它写出来的断言只有"恰好没变化那天"有意义，
而这正是这一晚反复栽的坑。所以报告全是合成的，日期自己定。

```
没关注→空且结构完整 / 关注了但没变→空 / 关注学校有新增→命中 /
关键词命中 changed→命中 / reparsed 一条都不出现 / 取关后不命中 / 重复关注只有一条
+ since 早于记录要显式说被夹 / 完全没有记录时不说"没有变化" /
  同一公告多次变化只提醒一次 / 查询参数名传错会静默回落 /
  digest 和 changes/history 的口径对得上
```

**"能点进详情"这条是真走通的**，不是断言绕过：把合成记录写进临时 JSONL、
用真的 `NoticeStore.load` 读进来，所以 `notice_id` 真的能在 `/api/notices/{id}` 取到。

### ⑤ 口径对齐

`history` 新增 `days_with_user_changes`（只算 `added`/`changed`），
原有的 `days_with_changes`（五个桶全算）**保持不变** —— 它回答"管道每天在跑吗"。

两个常量放在 `changes.py` 里当**单一事实来源**（`WORLD_CHANGED_BUCKETS` /
`OUR_PROCESS_CHANGED_BUCKETS`），`digest` 和 `history` 都从它取。
各写一遍就会漂移，漂移的表现是"history 说那天有变化、digest 不认识那天"。

不这么做就会出现互相打脸：history 说"过去 7 天有 3 天有变化"、
digest 说"你的提醒是空的"，用户会认为**有一个是坏的**。
有一条专门盯这个的用例（`digest_和_changes_history_的口径对得上`）。

**顺带发现**：真实 `index.json` 的 `days[]` **没有 `reparsed` 列**，
所以现在 `days_with_changes` 看不见"只有 reparsed 的那天"，两个字段完全一样、
区分是潜伏的。测试里显式写了这一列才能验出差异。**这条要 A 补**（第 5 次提了）。

### ⑥ 两条红灯 + 清掉"假设数据塞得进几页"

**改法不是把 50 改成 100**，是加了 `fetch_all(client, path, params)`：
按 `MAX_PAGE_SIZE` 一页一页取到 `total` 为止，`total` 是接口给的权威值、不猜。

两条红灯的病根分别是：一条只读第一页（50 条恰好全是"其他"，
所以"身份/机构两类都要有"直接红）；一条硬编码取两页（50+50=100 < 259，
漏掉的 159 条里可能整类都没被筛过，而断言还是绿的）。

**我顺手把排序那两条也改了** —— 它们在 72 条公告上用 `size=50`，
只验了前 50 条。这类**"悄悄变弱"比变红更坏**：红了你至少会去看。

按你说的，我把"哪些该改"筛了一遍：筛选用例里大量的 `params={"size": 50}`
断言的是**当页内的不变量**（`all(... for i in body["items"])`），
不受总条数影响，**不该动**。真正需要全量集合的只有那四处。

### 这一场我自己犯的三个错（都真有后果，不是笔误）

**1. `state.add_watch` 返回 `(watch, created)`，我在调用处按 `(created, watch)` 解包。**
→ `public_view(True)` → `'bool' object has no attribute 'get'`。
两个元素、类型还不同、顺序全靠记 —— 改成返回 `{"watch":…, "created":…}` 字典，
键名自己说明顺序。**这类 bug 用元组就是迟早的事。**

**2. 契约写 `?user_id=`、代码声明 `user`。**
现有三个接口（`/api/me`、`/api/posts`、`/api/notices/{id}`）都是 `?user=`，
我却在契约里另写了一个名字。后果最难发现：**传 `?user_id=u_t` 不报错**，
FastAPI 忽略未知参数、回落到 `u_demo`，表现是"所有关注都消失了"。
按"沿用现有假鉴权"改成 `?user=`，并加了一条用例把这个回落行为钉住 +
所有用户态响应都**回显 `user_id`**，调用方能自己发现传错。

**3. 把"日期被夹了"写进 `message`，然后被后面的结论覆盖掉了。**
按契约必须显式告知用户，而实际用户什么都看不到 ——
**更糟的是我那条测试还通过了**，因为命中消息里恰好也含 `2026-10-16`。
改成单独的 `notes[]` 数组（结构化），测试改成读数组。
和之前给套磁信加 `cited_from` 是同一个教训：**自然语言不是数据**。
