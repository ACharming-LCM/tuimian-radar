## 给 B

### 1. 【最要紧】`POST /api/letter` 做成**模板版**，不要等 LLM

你文档里写的是「依赖 LLM，模型和 key 未定，团队拍板前不做」—— **这个判断在当时是对的，
但现在情况变了：它是演示脚本第 4 步，是死的。** 而 LLM 那个决定一直没拍。

**不需要 LLM 也能做，而且做出来更有说服力：**

```
请求：{ "notice_id": "...", "profile": {...} }
响应：形状**照 contracts/fixtures/letter.response.json**（那个我已经生成好了）
```

- `citations` **全部取自真实公告原文**，逐条可回链（fixture 里 4 条就是这么来的）
- 响应里必须带 `"method": "template"`，并且**说清这不是模型生成的**
- 正文用模板拼：引用公告标题 + 引用 1~2 句真实的申请要求 + 留 `____` 给用户填自己的信息

**为什么这样对**：演示时最有价值的**不是信写得好不好，是 citations 逐条能点回原文**——
那是设计上防"模型编造导师信息"的手段，是真正有意思的部分。
而 LLM 一旦接上，`citations` 必须仍然逐条可回链，所以**这套机制现在就该建好**。

页面上会明确标「模板生成（未接模型）」。**这是诚信，不是减分。**

### 2. `GET /api/changes/history`

我这边新增了每日归档（`tools/run_daily.py`）：

```
data/out/history/index.json    索引：每天几号、多少条、增删改多少
data/out/history/<日期>.json   当天的差异报告
data/out/history/<日期>.jsonl  当天的精简快照（约 25 KB）
```

**这个接口是"月度订阅"唯一能拿出来的凭据。** 演示时被问"你怎么证明每天在跑"，
答案不该是"我们的脚本能跑"，而是**"这是我们过去 N 天的记录，这是每天的增删改"**。

返回 `index.json` 的形状就行（加个 `records_total` 之类的汇总更好）。

## 给 C

### 1. 【唯一剩下的脚本缺口】画像录入表单

你自己的彩排结论：**「匹配结果页现场填一个真实背景」走不通，缺画像录入表单。**

这是演示第 2 步的核心动作 —— 现场填一个人的真实背景，看它推什么。
表单不需要复杂，但字段要够：专业、成绩排名、英语、科研经历、目标学位。

**做完之后，"5 步全通"。**

### 2. 匹配页那 28 张「截止日待确认」，答辩会很难看

你提的这条判断很准：**30 条里 28 条显示"待确认"，评委看到的是一个坏了的功能。**

但**不要为了好看去猜日期**（我们定了不许猜）。正确的改法是**改展示，不改数据**：

- **卡片上有截止日才显示那个 chip；没有就什么都不显示**（现在是显示"待确认"，满屏都是）
- **详情页**才写清楚：「公告未明确截止日期，请查看原文」
- 演示话术我建议这样说：**「截止日期只有 31% 的公告能从正文里抽出来 ——
  很多学校把日期放在附件或图片里。我们标'需确认'，而不是猜一个填上去。」**
  这句话把短板变成了设计原则，而且是真话。

### 3. 接 `/api/changes/history` 做「过去 N 天」

B 上线接口之后，今日更新页加一块：**过去几天累计新增多少**。
这是月度订阅的素材，也是「每天更新」最直接的证据。
