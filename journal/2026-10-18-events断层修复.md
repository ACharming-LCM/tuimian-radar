# events 断层修复（2026-10-18）

**最终快照 = 1119 条 / events = 1131 条 / 取数时刻 2026-10-17 23:37:23**

## 一、根因（结构性，不是一次失误）

`run_daily.py` 的日更步骤里**从来没有生成 events 这一步**：只有抓公告、抓导师、院系清单、
归档、fixtures、数据门禁。`changes.json` 由 crawl 每轮覆盖写，而 `events.jsonl` 只能靠手跑
`tools/make_events.py --write` 追加。

所以每次日更之后事件流都停在原地：
- `notices.jsonl` 1119 条（10-18 01:27 的规则回填后写出）
- `events.jsonl` 476 条（10-17 19:27 的 470 条时代产物）
- 1119 条公告里 **655 条没有任何事件**（正好是新增的 655 条，含上交 47 / 川大 31）
- **12 条事件指向的公告已经不在产物里**

B 的推送链路只读 events.jsonl，所以这 655 条在"今日更新/推送"两页上是隐形的。

## 二、代码改动

### 1. `collector/tools/make_events.py`：新增 `--daily` 模式

`daily()` 一次做三件事，**共用同一份 seen 集合**：

1. 读 `changes.json` → 本轮变更事件（`build()`，原有逻辑不变）；
2. **存量覆盖**：任何一条没有 `added` 事件的公告都补一条（`at` 取 `crawled_at`，
   即"我们第一次抓到它"的时刻，不是现在、也不是发布日）；
3. **自检**：重新读**落盘后**的 `events.jsonl` 与 `notices.jsonl` 对账——
   无事件公告数、悬空事件数。覆盖有缺口时 **返回 1**（日更因此变红）。

幂等靠 `event_id`（`sha1(type|notice_id|内容指纹)`，**不含生成时间**），
另加一个内存 `seen` 兜住"同一条公告既在 changes.added 又在存量补"的情况。

新增 `--audit`：只对账不写，给排查用。

### 2. `collector/tools/run_daily.py`：接入"生成事件"步骤

位置在**归档/fixtures 之后、数据门禁之前**（`changes.json` 已由抓公告那步写好，
`record_stability` 和门禁要看到这一轮完整结果）：

```python
steps.append(run("生成事件", ["tools/make_events.py", "--daily", "--write"]))
```

`run()` 本来就把 `exit != 0` 计入 `hard` → 整轮 `sys.exit(1)`，所以**失败会红**，不会被吞。

结论行放在 stdout **最后一行**（`run_daily` 只打印子进程最后 6 行，悬空明细会把它挤掉）：

```
生成事件：新增 655 条 / 事件总 1131 / 公告 1119 / 无事件 0 / 悬空 12
```

## 四、复现时撞出的第二个结构性问题：events.schema.json 过期

`tests/test_events.py` 一开始是红的：

```
❌ 1 个用例失败：['每行都过 events.schema.json']
  'contact', 'materials' were unexpected
```

原因：10-17 `field_state` 从 4 键扩到 6 键，`notice.schema.json` 同步了，
**`events.schema.json` 没同步**。旧 476 条事件是 4 键时代的产物（违规 0 条），
新生成的 655 条是 6 键 → 全部违规。也就是说**只要日更开始生成事件，这个校验必红**。

修法：`events.schema.json` 的 `field_state` 增加 `materials` / `contact` 两个**可选**属性，
`required` 仍是原来 4 个。不能把新键设成 required——那会让 476 条历史事件全部非法。
消费方读不到这两个键时按 `unknown` 处理，不许当成 `absent`（已写进 schema 描述）。

改完 `test_events.py` → ✅ 全部通过；`test_data_contract.py` → 0 失败 / 1 警告（方向覆盖，既有）。
