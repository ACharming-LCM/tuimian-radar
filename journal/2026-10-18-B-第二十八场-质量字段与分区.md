### ⚠️ 一处我改了自己的主意（值得记）

我本来打算让接口层**按 `publish_date` 现算** `is_fresh` / `age_days`，
理由是 `HANDOFF-B` §5.3 那个 `freshness_hours` 快照坑。

**改掉了。** 因为数据层的 docstring 写得很明确：

> 这需要把"新"变成字段，**而不是让每个下游各自拿 `publish_date` 和 today 相减**

两个理由：
1. 两套时钟会打架。这个项目已经栽过四次"同一件事两处实现"。
2. **列表 fixture 是逐字段严格比对的。** 现算的话 `age_days` 每天变一次，
   fixture 从第二天起就与接口不等 —— 门禁天天红，而红的理由和代码无关。

代价是这两个值会随管道停止而冻住，已写进契约 §19.4 和 CHANGELOG。
**推送项是例外**：`events.jsonl` 里没有这两个字段，那里按 `publish_date` 现算 ——
这个不对称也写进契约了。

## B3：`/api/updates` 与 `/api/library`

| 判据 | 结果 |
|---|---|
| `updates` ≤50 条且全部 30 天内 | ✅ **27 条**，全部 7 天内（`days=7` 默认） |
| `library` 按学校/年份筛 + `is_historical=true` | ✅ 学校 175 条；`year=2027` **163 条**；`historical=true` **972 条** |
| 并集 = 全集，交集 = 0 | ✅ **27 + 1104 = 1131**，交集 0（门禁有断言） |

```
updates = 发布日 ≤ days 天（默认 7）且未过期且非 junk
library = 其余全部（补集，不是另外查一遍）
```

### 三个我踩到/差点写错的点

1. **两边 `days` 不一致 → 交集直接不为空。** 我先只给 `updates` 加了 `days`，
   用 30 天测，而 `library` 还是默认 7 天 → 8~30 天那批**两边都出现**，
   加起来 1216 ≠ 1131（多 85 条）。是恒等式断言把它抓出来的。
   修法：`library` 也收 `days`，默认一致，契约里把"必须传同一个值"写成硬要求。
2. **`is_historical` 不能按"在 library 里"标。** 资料库按发布日降序，
   第一页很可能全是"20 天前、不是本周、但也不是历史"的记录。
   按所在接口标，就是让同一个词在两个接口里指两件事。改成按 **30 天 + 未过期** 判。
3. **`?year=2027` 只比发布年 → 0 条。** 而这个产品的年份是**招生年**，
   2027 年招生的公告往往是 2026 年发的。改成同时认
   发布年 / `admission_year` / `target_year`，实测 163 条。

### "没读到截止日"不算过期

只有 `deadline.state == "found"` 且 `days_left < 0` 才算过期。
`unknown` / `absent` 被当成过期，代价是**一条还能报名的公告被归档进资料库**，
而用户不会去资料库找它。这是 §14 那条不变量的第四次落点。
