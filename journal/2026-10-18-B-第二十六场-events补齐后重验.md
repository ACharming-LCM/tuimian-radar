## 我这个"验证方式"自己先错了一次（这一场最值钱的）

第一轮量出来是 **475 / 1130**，而 A 那边是 476 / 1131 —— **两边都恰好少 1**。
差一致地偏移，通常不是数据问题，是量法问题。查下来确实是：

```powershell
# 我原来这么取基线
git show 0cccc6a^:data/out/events.jsonl | Out-File -FilePath before.jsonl -Encoding utf8
# → head = b'\xef\xbb\xbf{'   文件头有 UTF-8 BOM
```

`EventStore` 是逐行 `json.loads`，**带 BOM 的第一行解析失败会被静默跳过**。
行数其实是对的（476 / 1131），丢的是**第一条事件**。

改法：走 `subprocess` 取字节，不经过任何编码层。

```powershell
cmd /c "git show 0cccc6a^:data/out/events.jsonl > before.jsonl"
# ✗ 别用：cmd 里 ^ 是转义符，`0cccc6a^:...` 变成 `0cccc6a:...`，
#   于是 before 和 after 被写成同一份（两个文件字节数一模一样，692833）
```

最后在 `measure_push_volume.py` 里用 `subprocess.run(["git","show",...], stdout=PIPE)`
取 `bytes` 直接 `open(...,"wb").write()`，这条链路才是可靠的。

**教训（和 §7.3 / §7.8 同一类）**：数字对不上时，先怀疑自己的量法，
尤其是"偏差恰好是 1"这种整齐的数。如果我当时直接采信 A 的 476，
我就会在 journal 里写下"我测出 475、A 说 476，数据可能有抖动"——
一句完全错误的结论，而且看起来很像认真核对过。
