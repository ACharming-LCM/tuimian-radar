## ① 小 bug：`?limit=1&foo=bar` 把 `limit` 报成未知

根因：B24 的白名单只写了"我们**实现**了哪些参数"，而 `limit` / `offset`
是**约定里的合法参数**（`size` / 分页的别名）—— 于是合法参数被当成未知。

修法不是"把它们加进白名单"（那只会在新位置继续静默失效），而是**真的实现**：

- `limit` = `size` 的别名；**同时给时 `size` 优先**（更明确的名字优先）；
- `offset` = 从第几条开始，优先于 `page`；响应里的 `page` 按 offset 算好再回显
  （`offset=3&size=3` 与 `page=2&size=3` 返回**同一批 id**，门禁盯着）；
- 顺带补 `topic`（`apply` / `non_apply` / `other`，逗号多选，错值 400 `BAD_TOPIC`）——
  它也是"合法参数"，不实现同样是假功能。

白名单现在 = `school / unit / apply_mode / level / year / q / sort / page / size /
meta / age_tier / include_junk / notice_kind / topic / limit / offset / deadline_within`。

**留了一条断言防回归**：`?size=1&limit=1&offset=0&foo=bar&baz=2` 的
`unknown_params` 必须只有 `["foo","baz"]`。

## ② `sort=deadline_asc`：`deadline=None` 沉底

排序本身早就是"found 升序 → unknown → absent"，但**没有断言钉住**。
这次加了：第一页里"有日期的都在没日期的前面"、found 内部升序，
并且**翻到最后一页要求 `deadline` 全为 `None`**（只验第一页说明不了沉底）。

> ⚠️ **一个要用户拍板的观察（我没动）**：升序会把**已截止的**排在最前面 ——
> 实测前 5 条是 2010 年的截止日。因为契约 §14 的分桶对 `found` 一视同仁
> （found 就是按日期升序）。学生点"按截止日"想看的是"哪条快截止了"，
> 2010 年的已截止显然不是。要不要把已截止也沉底（found 内再分「未截止/已截止」），
> 是**产品判断**，改了会和 §14 的"三态分桶"定义一起动，所以我留着等你说。

## ③ `deadline_within=1/3/7/30`

- 只算 `found` 且 `0 <= 剩余天数 <= N`；
- **不含已截止**（用户问的是"还来得及的"）；
- **不含 `unknown` / `absent`**（那是替公告编一个截止日，三态不变量）；
- 别的值 → 400 `BAD_DEADLINE_WITHIN`（只给四档：`0`/`9999` 各写一套语义没有意义）。

实测：1 天 **3** 条 / 3 天 **7** 条 / 7 天 **18** 条 / 30 天 **24** 条。

## ④ `/api/facets` 加 `deadline_buckets`

8 个桶（`expired` / `within_1` / `within_3` / `within_7` / `within_30` /
`later` / `unknown` / `absent`），带 `label` 和真实条数。
**和筛选同一套口径**：`within_7.count == ?deadline_within=7` 的 `total`
（前端下拉写「7 天内 (18)」，点进去不会对不上）。

实测：expired 692 / within_7 18 / later 12 / unknown 525 / absent 1166；
恒等式 `within_30 + later + expired + unknown + absent == 2419` ✅。

> `within_N` 是**累计**桶（0..N 天），**不能相加**；文档里写明了。
> `unknown` 和 `absent` 分开：前者要用户看原文，后者是确定回答。
