## B（后端）— 第十五场：把"验收标准"这条松口拧紧

> 接任后第一场正式署名 B（交接时署过一篇 `2026-10-17-E-第一场.md`，
> 从这篇起用回 B，序号接着往下排）。
> 用户这场的原话是「把最薄弱的地方先坐稳」，所以只干一件事。

### 最薄弱的地方是哪个：**不是功能，是"验收标准"有一半在自证**

我把这一层过了一遍，真正紧的不是任何接口，而是 `run.py` 里那一行：

```python
LISTING_SORT_FIXTURE_STALE = True
```

它的作用是：**列表响应的排序那一半，不用 fixture 比，而是用例自己调
`listing_sort_key` 算出期望值再和接口比。**

这跟交接文档 §7.3「断言看起来在验，其实在赌」是同一类，但更隐蔽 ——
`§7.3` 那个是"两个数恰好相等"，这个是**期望值和被测代码用同一个函数**。
只要那个函数是确定的，这条永远绿。**它验的不是"排序对不对"，是"函数会不会随机"。**

### 关键发现：这个松口的理由早就消失了，没人对账

B 当初设这个开关是因为"排序策略改成 `(relevance, publish_date)` 降序了，
而 fixture 还是旧排序的快照"。**但我实测：**

```
fixture total = 196          数据 total = 196
前 50 条逐位置相同 = 50/50
fixture 那 50 条今天仍在数据里 = 50/50
```

**D 在 `b921ec9`（`08:44`，栏目发现第二层 108→196 条）就重跑过
`make_fixtures.py` 了。** 也就是说这个开关从那一刻起就可以拧紧，
而它挂了一整晚，还被写进交接文档当"挂着的第 4 件事"。

**这是"锁着一个已经不用锁的门"。** 危害不是排序错了，是：
① 排序那一半的真实约束**一晚上都没被验过**；
② 下一个读注释的人会以为 fixture 不可信，于是继续用现算兜着；
③ 而交接文档还教他去"把开关改成 `False`"——**改 `False` 也只是让它今天紧**，
明天谁再想松一下就又松了。

### 改法：**删掉开关**，不是改成 `False`

- 规模不同 → 直接红，并明说**这不是接口坏了** + 给出重跑命令。
- 规模相同 → `got["items"] != fx["items"]` 逐位置逐字段严格比。
- 不一致时调 `_why_list_mismatch(...)` 生成归因消息。

**归因原则：默认怀疑接口。** 只有逐字段证明"接口给的值 == 磁盘上的值"，
才敢说"接口是忠实的，问题在 fixture 过期"。
反过来归因（把 bug 说成数据旧）是最坏的一种错：它会让人去重跑 fixture，
**然后红变绿、bug 还在**。所以代码里 `mismatched` 那一支专门输出一句
「重跑 fixture 会把问题掩盖掉」。

### 反向验证（5 个场景，全部按预期）

| 注入 | 期望 | 实际 |
|---|---|---|
| 不注入 | 绿 | ✓ 绿 |
| fixture `total` 少 1（模拟数据涨了） | 红在规模，指向 make_fixtures.py | ✓ |
| fixture 第一条标题改坏 | 归因"接口忠实，fixture 过期" | ✓ |
| fixture 交换前两条（旧排序） | 归因"接口顺序 == 现算顺序 → fixture 是旧排序快照" | ✓ |
| **接口第一条标题 ≠ 磁盘** | **指认接口**，不许开脱 | ✓ 还专门提示"别重跑 fixture" |

第 5 个场景是最要紧的：**归因机制必须有"指向自己"的能力**，
否则它就是一个只会替代码开脱的辩护律师。

### 顺带纠正一处不准确的旧说法

`docs/HANDOFF-B.md` §5.1 写着"列表还比**键顺序**"。
**代码从来没有比过键顺序** —— `dict == dict` 在 Python 里不比较键的先后，
而下面那条 `列表项字段与_fixture_一致` 的 docstring 明确写着"键序不是契约"。
我在新注释里纠正了：这里比的是**内容 + 逐位置顺序**。

这条本身不重要，但它说明同一份文档里"我以为在验的东西"和"实际在验的东西"
可以不是一回事 —— 跟这个开关是同一个病。

### 我自己又踩了一次 §7.9

写反向验证脚本时，字符串里用了 ASCII `"` 当中文引号 →
`SyntaxError: Perhaps you forgot a comma?`，**一字不差地复现了交接文档里那条记录**。
改成 `「」` 就好了。（这条我第一次注意到它，就是因为 B 说"我一次犯了两处"。）

### 一处我**读错**了、必须记下来

我一开始判定「`META.json` 的 `_as_of: 2026-10-16` 是假话，因为 fixture 里是 196 条
（10-17 的数据）」。**这个判断是错的。**

`_as_of` 的语义是"计算时假装今天是哪天"，用于 `score` 的 freshness 分档、
`days_left`、`dropped_expired` 这些**依赖日期**的量。
它跟 `notices.list.json` 里有几条**没有关系** —— 那个文件只依赖数据。
所以 META 没撒谎，是我把两个不同的分母读到一起了。

**这正是交接文档 §1 那个教训的镜像**：B 把「68.9% unknown」读成"我们失败了 135 次"，
我差点把「as_of 10-16」读成"元数据造假"。
**同一个坑，换了个方向。数字要读，但先把它的分母读明白。**

### 现在这条门禁的代价（我有意接受）

如果 D 涨了数据但**没重跑 `make_fixtures.py`**，这条会红，而红的原因不在我这一层。
这是**有意**的：fixture 是 C 降级演示的数据源（`?api=fixtures`），
它落后于数据，降级路径就会给用户看旧数据 —— 那本来就该被看见。
而红的**第一句话**就是"这不是接口坏了 + 去跑哪条命令"，
所以它不会变成那种"红了但没人知道该干嘛"的门禁。

**没加新用例**：这条本来就在，只是从"自证"换成"真验"。

### ① 另一个 agent 做了**同一件事**，只是选了另一种写法

`origin/main` 里那行变成了：


**它也发现了这个松口，也核了 50/50，也拧紧了。** 两条独立的判断指向同一个结论 ——
这本身是好消息（说明这不是我一个人的洁癖）。

它写"**按键顺序**完全一致"——**结论对，理由错**：`dict == dict` 在 Python 里不比键序，
键序一致是被 `==` 的内容比对顺带带出来的，不是被"键序比对"验出来的。
我把这句纠正写进了注释：**同一份代码里"我以为在验的"和"实际在验的"不是一回事**，
这个病和那个开关是同一种。
