- 2026-10-19 B（后端）: **B25 修正：`deadline_asc` 只排未来 + `deadline_desc` +
  facets 互斥桶。** 破坏兼容：**否**（`sort=deadline_asc` 的**语义**修正 ——
  已截止的默认不再出现；加 `deadline_desc` / `include_expired`；
  `/api/facets` 加 `deadline_exclusive_buckets`）。

  **① `sort=deadline_asc` 之前把 2010 年的排最前**
  用户实测前 5 条是 2010-05-31 / 2010-06-10 …（16 年前的已截止公告）。
  "按截止日排序"要回答"哪些快来不及了"，不是"哪些早就过期了"。现在：

  ```
  future（deadline >= 今天，日期升序）
    → [仅 include_expired=true] 已截止（日期降序，刚过期的先）
    → deadline 为 null（absent / unknown）沉底
  ```

  - 默认**已截止一条都不出现**（实测 asc total 1727 = 36 条未来 + 1691 条 null）；
  - `deadline` 为 `null` 的仍沉底、不参与主序列（`total` 里还算它们，
    所以 1727 不是"只有 36 条"，别误读）；
  - `include_expired=true` 时已截止排在**未来之后、null 之前**（实测 total 2419）。

  **② 新增 `sort=deadline_desc`（过期优先）**
  `deadline_asc` 的镜像：已截止（刚过期的先）→ 未来（最远的先）→ null。
  用户原话"想看已过期的用 `sort=deadline_desc`"，所以它不是"未来最远的先"
  （那样过期记录会沉到最底下，等于看不到）。实测第一条 `2026-10-18`（已截止）。

  **③ facets：写清累计口径 + 新增互斥桶**
  用户指出"六个桶相加 == total"是**他写错了** —— 我们的是累计桶
  （within_7 ⊃ within_3 ⊃ within_1），相加当然不等于 total（2447 vs 2419）。
  数据不改，契约里写明并加前端警告；同时给**互斥版本**：

  ```
  deadline_buckets           累计：within_N == ?deadline_within=N 的 total
  deadline_exclusive_buckets 互斥：within_1 / within_2_3 / within_4_7 /
                                    within_8_30 / later / expired / unknown / absent
  ```

  互斥桶实测：3 / 4 / 11 / 6 / 12 / 692 / 525 / 1166 = **2419**（== total，门禁盯着）。

  门禁 **224 → 226**（+2：`deadline_asc` 只排未来、`include_expired` 边界、
  `deadline_desc` 过期优先；旧的 `排序_deadline_asc` 用例按新语义改写，
  facets 用例扩成同时验两套桶）。


  **① 补 bug：`limit` / `offset` 被当成未知参数**
  用户实测 `?limit=1&foo=bar` 返回 `unknown_params: ["limit","foo"]`。
  `limit` 是合法参数，只白名单不实现等于换一种静默失效 —— 现在真生效：
  `limit` = `size` 的别名（同时给时 `size` 优先）、`offset` 优先于 `page`
  （响应里的 `page` 按 offset 算好再回显，保持自洽）。
  顺带补 `topic`（apply / non_apply / other，逗号多选，错值 400 `BAD_TOPIC`）。

  **② `sort=deadline_asc`：没截止日的**必须**沉底**
  这条排序早就有（分 found / unknown / absent 三桶），但一直没有断言钉住；
  新增断言：翻到最后一页，`deadline` 必须全为 `None`。
  ⚠️ 已知观察（**等拍板**）：升序会把**已截止的**（2010 年的）排在最前面，
  因为契约 §14 的分桶对 `found` 一视同仁。要不要把已截止沉底，见 journal。

  **③ `deadline_within=1/3/7/30`**（别的值 400 `BAD_DEADLINE_WITHIN`）
  只算 `found` 且 `0 <= 剩余天数 <= N`；**不含已截止**、**不含 unknown / absent**
  （后者是替公告编一个截止日）。

  **④ `/api/facets` 新增 `deadline_buckets`**
  8 个桶（expired / within_1 / within_3 / within_7 / within_30 / later /

  `within_N.count` 与 `?deadline_within=N` 的 `total` **一一对应**；

- 2026-10-17 A（凌晨）: **PDF 表格按行拼接（extract v4）+ 变更归因要靠抽取器版本。**
  **问题**（C 走查时先看到的，`journal/2026-10-17-C-走查.md` 的 #1 和 #6）：
  `pdf.py` 用 `page.get_text()`，表格会变成**一个单元格一行**：
  `序号 / 学院 / 姓名 / 学号 / 专业 / 1 / 化学学院 / 王某某 / …`。
  后果：公告详情正文是一列竖排的词，读不了；套磁信从正文挑引用句只能挑到碎片
  （有一条引文只有一个词「论文」）。
  **修法**：PyMuPDF 1.27 有 `find_tables()`。把表格和普通文字块**按纵向坐标排序后交错输出**，
  表格按行拼成 `a | b | c`。实测：93 个 PDF 里 67 个检出表格，共拼出 1866 行，零异常。
  **为什么不能在渲染层修**：正文是数据，数据里就是一列竖排的词，前端拼不回来。
  → `extract.version` 升到 **v4**。

  **由此引出的归因规则（重要）**：正文是我们**抽出来的**，抽取器一换正文必然不同。
  所以 `diff.py` 新增判据 —— **只有抽取器版本相同时，正文哈希差异才算学校改了内容**：
  · `changed` = 正文变了**且** `extract.version` 相同，或**附件 URL 集合**变了
  · `reparsed` = 抽取器版本不同带来的正文差异 / 只有派生字段不同 / 附件只有 `text_len` 变
  实测：不加归因的话，67 个 PDF 的正文改动会被日报说成「学校改了 67 份通知」
  （第一次跑出来是「有变化 13」，其中 13 条都只是 `text_len` 变了）。
  修完：**有变化 0 / 重新解析 21**，全部归因正确。
  → `reparsed[]` 多一个 `why` 字段（"抽取器版本变了" / "附件抽取结果变了" / "派生字段不同"）。
  → `data/out/history/*.jsonl` 的 SLIM 字段**必须含 `extract`**，否则跨天归因失效。
