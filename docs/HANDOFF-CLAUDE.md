## 0. 一分钟读懂

**产品**：给保研（推免）学生做的**推免信息聚合 + 决策辅助**。
把散在几十个学校研究生院 / 院系官网的招生公告、文件公示、导师名录聚合起来，每天更新，
再配背景匹配、套磁信、匿名论坛、付费墙。

**形态**：一个网页应用（9 个页面）+ 一个 FastAPI 后端 + 一条数据抓取管道。
**不是** PPT 项目，**不是**小程序。

**场合**：**比赛**，评委会是**商业向**的（不是技术评审）。所以"有没有人要"和"能不能讲清楚"
和"代码写得对不对"一样重要。

**当前状态**：技术三条线都跑通且门禁全绿；但**商业验证是空的**（没约到真保研生试用、
PPT 只有一个大纲、没有 .pptx 文件）。

## 1. 项目是什么，为什么值得做

保研（推免）信息高度分散：

- 同一所学校，研究生招生网和每个院系官网**各发各的**；
- 截止日经常只写在**附件 PDF** 里，甚至只在**扫描件图片**里；
- 导师的研究方向要一个个点进个人主页翻；
- 学生真实的工作量是：**每天刷几十个网站，怕错过一条报名通知**。

错过一条 = 错过一年。这是这个产品存在的理由。

**核心承诺（也是最难验证的一句）：每天更新。**
第 7 节会讲，这句话到现在**还没有被连续性验证过** —— 这是我认为交接里最该被接手人盯住的一件事。

## 4. 三个模块各自怎么工作

### 4.1 数据层 `collector/` —— 我负责的

**链路**：

```
sites.json(站点配置) → discover.py(找栏目) → listparse.py(解列表)
→ detail.py(解详情) → pdf.py(解附件) → fields.py(抽字段)
→ diff.py(变更检测) → crawl.py(组装)
→ data/out/notices.jsonl
```

**入口**：

```powershell
$env:PYTHONIOENCODING="utf-8"
Set-Location collector
D:\python.3.10.11\python.exe crawl.py --details 4       # 全量约 10 分钟
D:\python.3.10.11\python.exe crawl.py --details 0       # 冒烟（不写盘，秒级）
D:\python.3.10.11\python.exe tools\run_daily.py         # 每日流程（会 --refresh，真打 37 个站）
```

**产物**：`notices.jsonl`（唯一真相）、`changes.json`、`digest.md`、`coverage.md`、
`freshness.json`（给 B 的 `/api/freshness`）、`faculty.jsonl`、`history/`、`runs/`。

**字段可信度三态（`field_state`）是这个模块最核心的设计**，见 §5.3。

**导师链路**是 `faculty_sites.json`（**手工配置的院系 URL**）→ `crawl_faculty.py`。
四条解析路径按优先级：`li` 挂 `h3` / 表格有表头 / 姓名职称粘连 / 人名链接指向个人页。

⚠️ **导师层是"手工配置"能力，不是泛化能力。** 换一所学校不能自动跑。
所以**PPT 上不能说"支持多校导师"**，只能说"已跑通 6 个院系"。

### 4.2 后端 `server/` —— B 负责的

FastAPI，18 个模块，`server/tests/run.py` 有 **137 条契约门禁**（零第三方依赖，几秒）。

**一定要记住的接口约定**：

1. **默认响应形状 = `contracts/fixtures/` 里的 fixture，一个多余键都不加。**
   这是 B 立的规矩，理由是"加了新键，C 的比对和 fixture 回归就全废了"。
2. **`relevance` 故意不在列表载荷里** —— 不在载荷里，前端就没法拿它当筛选器，
   于是"只用于排序、绝不用于隐藏"这条规矩被**结构性地**锁死了。**别好心把它加回响应。**
3. **`unknown` 不许被当成 `absent`** —— 排序、统计、聚合三处都不许把"不知道"算成"没有"。

### 4.3 前端 `web/` —— C 负责的

9 个页面：匹配结果 `/`、公告列表 `/notices.html`、公告详情 `/detail.html`、
导师 `/faculty.html`、今日更新 `/daily.html`、论坛 `/forum.html`、
订阅 `/pricing.html`、套磁信 `/letter.html`、付费墙（详情页的一个态）。

每个页面都有**四态**（正常 / 空 / 500 / 超时）+ **375 手机宽度**的自查。

**两种数据源**：真接口 `/api/*` 优先，不通则退到 `contracts/fixtures/`。
页脚会标"数据源：真接口"或"本地样例"—— **这个标记必须如实**。

## 5. 契约与协作机制（不按这个来一定打架）

### 5.1 目录所有制

| 谁 | 独占目录 | 不许碰 |
|---|---|---|
| A（数据） | `collector/`、`data/` | server/ web/ |
| B（后端） | `server/` | collector/ data/ web/ |
| C（前端） | `web/`、`docs/` | server/ collector/ data/ |
| 共管 | `contracts/`、`journal/`、`issues/` | —— |

需要改别人的东西 → 写 `issues/`，不要直接动。

### 5.2 三个文件通道

1. **`journal/<日期>-<A|B|C>-*.md`** —— 单向广播，只追加。收工必写，五段式：
   做了 / 怎么验的 / 卡在哪 / 需要谁 / 契约动没动。
2. **`issues/NNN-*.md`** —— 需要别人决策的事。
3. **`contracts/CHANGELOG.md`** —— 契约变更，一行一条。

⚠️ **这三个通道只是"文件"，不是"消息"。** 对方不会收到通知，只有下次开工主动去读才看得到。
这条我踩过：我以为写了 journal 就算"派活了"，用户点出来「你外包他们收不到你的信息啊」。

### 5.3 最重要的一条设计：`field_state` 字段可信度三态

**问题**：`deadline: null` 一个值**同时表示两件完全不同的事**：

- 「这公告里就没有截止日」（读了全文，确实没有）→ 用户该放心
- 「我们没读到」（正文是兜底抓的 / 太短 / 是扫描件 / 被截断）→ 用户**必须自己去看原文**

对用户这是**反的**两句话。评审问"这个还能报吗"，如果答成"没有截止日"，
而实际上是"我们没读到"，那是最伤信任的一种错 —— **比直接说"不知道"差得多**。

**方案**：

```json
"field_state": {"deadline":"found|absent|unknown", "majors":…, "attachments":…,
                "body":"ok|generic|missing"}
"body_how": "selector|generic|none|file|incomplete"
```

- `found` 抽到了 ／ `absent` **正文读到了、内容足够，里面确实没有** ／ `unknown` **我们判不了**
- `absent` 的门槛**是量出来的，不是拍的**：正文必须来自**站点选择器**、
  ≥ **150 字**、且不是"只剩一个元信息框"、且没有被截断、且没有扫描版附件。
- **关键性质：三态只把结论往"不知道"那边退，永远不会往"有"那边走。**
  它不参与任何"编一个日期出来"的逻辑。

**必须写进契约的界面措辞**（C 直接照做，别自己拼）：

| `field_state.deadline` | 显示 |
|---|---|
| `found` | 显示日期 |
| `absent` | 「该公告未公布截止日」 |
| `unknown` | 「**未能读取截止日，请点原文核对**」（**必须带原文链接**） |

⛔ **绝对禁止把 `unknown` 显示成"没有截止日" / "暂无" / "——" / 干脆不显示。**
**不显示最危险**：用户会以为"这条没有截止日"，于是**不去看原文**。

### 5.4 fixtures 的时效性

`contracts/fixtures/` 里**形状是永久的，数值只对 `_as_of` 那天有效**。

**数据一变就必须重出**：`python tools/make_fixtures.py --as-of <日期>`。
不重出的话 B 的门禁会红，而红的原因**看起来会像"他的测试有问题"**（这个坑害过 B 两次）。

## 6. 我的看法（你问的"什么看法"，这部分是我的判断，可以不同意）

### 6.1 这个项目真正的护城河不是"抓取"

抓公告这件事，别人也能做，技术上不构成壁垒。**真正难的是三件事**：

1. **把"不知道"和"没有"分开**（`field_state`）—— 这需要承认自己抓不到，很多团队不敢做；
2. **每条结论都能回链原文**（套磁信的引文逐条回链、匹配的每条理由）—— 这是"可信"的机制；
3. **每天真的在更新**（这部分**还没验证**，见 §7.1）。

**我的判断**：如果只有"聚合了 196 条公告"，评委大概率会问"这不就是个爬虫吗"。
**能救这个产品的是第 1 和第 2 条** —— 它们把"信息多"变成"信息可信"。

### 6.2 数据规模已经够了，别再扩

196 条 / 17 校 / 557 导师。**继续加学校、加站点的边际收益已经明显下降**：

- 剩下 17 个产出 0 条的站点，大多是 **JS/SPA 或登录后可见**（上交、清华研招、川大），
  需要预渲染才能抓，投入产出比差；
- 而**已有 20 个站点的稳定性**比多 5 个站点更值钱。

**我的判断：先放着。** 如果接手后想动，请先读 `docs/FACULTY-ROUTES.md`，那里面记了三条
试过的系统性路子和它们的成色。

### 6.3 最该先做的是"启日更稳定性"，不是加功能

它是唯一能把"每天更新"从**承诺**变成**事实**的事，而且**需要时间积累**——
今天启明天才有第 2 条数据。越晚启越吃亏。

代码已经写好了（`collector/tools/run_daily.py` 里的 `fingerprint()` / `record_stability()` /
`continuity()`，24 条测试在 `tests/test_stability.py`），**但一次真跑都没跑过**，
`data/out/stability.jsonl` 至今不存在。

### 6.4 PPT 不是我的优先级，但可能其实是用户的

我上一轮建议"先做功能、PPT 放后面"，用户当场反驳：「**现在 ppt 不是优先的吧，应该先把功能跑通**」。
后来他又提出"鲁棒性"。

**我的看法**：他说得对，功能没跑通就做 PPT 是空的。**但要注意时间**——
现在 `docs/PPT-OUTLINE.md` 只有大纲（73 行），**没有任何 .pptx 文件**。
如果路演日期临近，这会是最后卡住的东西。**这个应该由你/他去判断，不是我去判断。**

### 6.5 一个可能被低估的风险：三个 agent 共用同一个工作区

我实际遇到过：我的门禁从 137/137 掉到 124/2，原因是 pull 进来别人的改动，激活了过期的假设。
**多 agent 并行的代价是"随时可能被别人改坏"，而报出来的现象像是"我的代码坏了"。**

建议接手后保持：**每次 pull 之后重跑门禁**；改任何过滤器/判据之后**跑全量并逐站点对账**
（不能只看总数涨了）。

## 7. 我没做到的事（诚实清单，按严重程度排）

### 7.1 【最严重】"每天更新"这句承诺没有被验证过

- `data/out/stability.jsonl` **不存在**
- 全量只跑过几次，**没有连续两天的记录**
- 代码和 24 条测试都在，但**一次真跑都没有**

**为什么没做**：真跑一次要 10 分钟、会真实请求 37 个学校站点，需要用户点头；
挂 Windows 计划任务要改系统设置，也要他同意。我一直等到交接也没等到这个"点头"。

**接手后第一件事建议**：说服用户跑一次 `run_daily.py`，然后每天跑。
半年后"连续 30 天"就是最有说服力的一句话。

### 7.2 17 个站点产出 0 条

原因已分诊：JS/SPA 或登录后可见，需要预渲染。**我的判断是先放着**（见 §6.2），
但要让你知道这个数字：**净覆盖 20/37**。对外说覆盖率时别只说 37。

### 7.3 导师层是手工配置能力，不是泛化能力

6 个院系跑通了，换一所学校不能自动跑。而且**大连理工那 233 人是"名录级"**
（全校教师、方向只有 42%），**不许并进匹配级数据假装覆盖率**。

### 7.4 `data/out/runs/<日期>.json` 没做

B 的 `/api/admin/crawl` 里 `steps` 恒为 `null`，因为他没有解析我的
`data/out/runs/<日期>.md`（那是对人文档，格式说改就改）。要做机器可读的运行明细得加这个。
**不加也完全能跑。**

### 7.5 套磁信的引文仍有损

后端这一轮把**表格行**从引文里删掉了（纯表格式公告不再引表格），但
`materials` 里的两字项（如「论文」）**故意没加长度下限**——加了会连带砍掉"身份证""成绩单"。
这是个待定判断，不是漏做。

## 10. 坑清单（这一节最值钱，别嫌长）

下面每一类都**真踩过**，有的踩了两次以上。

### 10.1 「今天的数据刚好装得下 N 页」

**栽过 5 次。** 测试断言绑了"当前磁盘上恰好是什么数据"：
额度状态文件残留 / 断言绑学校名 / 断言"现在磁盘上是空报告" / 硬编码页数 /
**"低置信度的第一条恰好是哪一条"**（最近一次，是我自己写的用例）。

**正确做法**：绑**结构 + 不变量**，或者循环取到 `total` 为止，或者**自己造数据**。

### 10.2 「同一个策略写在两个地方，迟早分叉」

**栽过 4 次**，而且每次都是**改了副本没改原件**。最近的例子：
- `make_fixtures.py` 的排序口径没跟上服务端 → fixture 与接口顺序只重合 26/50
- 我把"留存率 80%"的阈值写在 `crawl.py` 和门禁两处 → 现在改成 `common.MIN_RETAIN_RATIO` 一处
- **举例里的省略号必须写明"这是省略"**（契约例子里的 `…` 被生成器读成"要截断"，红在了两边都没做错的地方）

### 10.3 「一个判据只在部分站点上出错时，最容易瞒过去」

为了配"文章不是栏目"的反向闸，写过 `/\d{5,}/`（想当然"长数字就是文章 id"）。
可维普 CMS 的栏目 URL 就是 5 位栏目号，**浙大材料那一页 136 个栏目全被这道闸杀掉**，
该站记录 **6 → 0**。别的学校没炸，只因为它们的栏目名是字母。

**所以：改任何一个过滤器，都要跑全量并逐站点对账，不能只看总数涨了。**

### 10.4 「在"生成候选"阶段就失败的过滤器，不会在"拒绝原因"里留下痕迹」

`LIST_HINT` 只认维普/正方的 URL 形状，而上交/清华/川大的栏目是路径式、没有扩展名，
**候选在算分之前就被全筛掉**。后果：`with_rejected=True` 里**拒绝数是 0**，
报告看起来像"这些站点没有栏目"，而它们首页上的招生类链接其实有 149 个。

**教训：报告"我拒绝了什么"是不够的，还要报告"我根本没生成候选"。**

### 10.5 「差一个字就漏」

`BOARD_NEG` 里有「党建」，而清华物理系的栏目叫「**党团**学工」——差一个字没匹配上，
党建/工会新闻被抓进来 3 条。

### 10.6 「一条脏数据同时打红两条门禁，报出来像两个问题」

那 3 条新闻的列表页不带日期 → `publish_date` 是 `None` →
① 违反 schema（要求 `string`）② B 的排序测试崩溃（`str` 与 `None` 不可比）。

**根因只有一个。遇到多条门禁同时红，先怀疑共同根因，别分头修。**

### 10.7 「排序键和展示字段抽错，比一个字段缺失严重得多」

南开一条通知：页面真实发布日 2026-04-13（URL 里也写着），我们存的是 2026-05-14
（正文里「材料审核结果发布时间：2026年5月14日前」）。

因为 `publish_date` **既是排序键又是展示字段**。而且它反向害了截止日：
截止日要求 ≥ 发布日，发布日被推后 31 天，正文里 2026-04-28 的报名截止就被噪声闸
**正确地**拒掉了。**一个错字段把另一个正确字段拖下水，报出来却像"截止日抽不到"。**

修的时候又踩一个：把正则放宽成裸 `时间[：:]`，匹配上「**截止**时间：2026年4月28日」。
**放宽一个正则时要顺手问一句：它还能匹配到哪些我不想要的东西。**

**可复用的方法：找"数据自带的对照物"。** 维普系 URL 里写着 `/YYYY/MMDD/`，天然基准。
用它量：旧 88.5% → 最终 98.1%。

⚠️ **量的时候我也错了两次**：第一次只比 `detail` 单干的结果，忘了真实记录是
`detail 日期 or 列表页日期`，报出"99 条丢失日期"的假象。**先想清楚"我在比什么"，再去比。**

### 10.8 【我自己这一轮踩的】验证条件写错，会把好数据报成坏数据

我做 `field_state` 离线回填时，**要求"产物正文 = 我按《附件正文》标记拼出来的那串"**，
于是 **28 条被判成"对不上"** —— 而它们其实没问题，只是附件正文的分隔符不止一种写法。

**判据要挑真正的不变量（前缀关系），不要挑"我复现出的那种具体拼法"。**

同一个病第二次：数据门禁里**拿 HTML 解析器去重放文件型记录**（它们的正文其实在 PDF 里），
6 条正常记录被判成"对不上"。**校验方法用错对象，和校验条件写错一样，都会把好数据报成坏数据。**

第三次（这一轮最值钱的一个发现）：我上一轮做了"三态"防"没读到被说成确实没有"，
结果从**"整页只到了一半"**这个口子漏了同一件事 —— 实测把 1400 字正文截到 232 字，
`body_how` 还是 `selector`、长度照样过 150、`body_state` 照样是 `ok`，**照样敢说 `absent`**。
现在用 `</html>` 结构判据挡（`body_how = "incomplete"`）。

### 10.9 「我开的 subagent 和真正的 B/C 抢同一个目录」

我中途开了两个 subagent 替我干后端/前端，结果：

- 它们和用户自己那两个 B/C 会话**在同一个工作区改同样的文件**
- 用户点出来：「**你自己下发的agent不归我管**」
- 我停掉它们，把 900 行半成品挪到 `wip/subagent-round2` 分支，main 保持干净

**教训**：**先搞清楚"这个活归谁"再派活。** 派给"我自己的手"和派给"另一个独立的会话"
是完全不同的两件事，后者需要文件通道 + 用户转交。

### 10.10 「不要用 subagent 做验证」

实测教训：83 个 agent 跑核验，其中 45 个因为余额不足直接失败，
而失败的被裁决逻辑**静默算成"这条不成立"** —— **失败被伪装成结论**，比浪费钱更危险。

**核验一律主 agent 内联做：Grep → Read → 比对。**
只有"独立转录手写图像、取多数一致值"这类必须多方独立的任务才值得 fan-out。

### 10.11 硬规矩（违反会出事，不是风格问题）

1. **绝不编造截止日。** 抽不到就 `null` + 警告。**编造的截止日比 null 危险得多**
   —— 用户会照着一个假日期安排。
2. **`relevance` 只用于排序，绝不用于隐藏。** 一个不可靠的相关性信号可以**排序**，
   永远不能**藏掉**结果。
3. **绝不编造导师。** 一条假导师比少一条真导师严重得多。
4. **失败必须带原因。** 所有失败路径都要能分类（`truncated` / `tls_handshake` / `js_app`），
   否则永远查不清。"解析失败"四个字等于没写。
5. **宁少不假。** 名录级数据不许并进匹配级数据假装覆盖率。
6. **说了做不到的事要在文档里写出来。** 半成品配诚实的说明，比假装做完强。
