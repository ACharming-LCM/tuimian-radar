# 远程伙伴必读（先读这份，再看你的任务书）

## 这个项目在做什么

一个帮应届本科生选推免（保研）的信息系统：抓各校研究生院和院系的招生公告，
结构化、按背景匹配、并给出**导师/实验室**这一层的数据。

**你们拿到的是一个"快照包"，不是实时仓库。** 这一条决定了下面所有规矩。

## 一、快照点

**你的快照点写在包根目录的 `MANIFEST.md` 里**（第一行）。

> 这里**刻意不写具体 sha**。我一开始硬编码了一个，结果打完包就已经是另一个提交了 ——
> 手写的文档不该写脚本能生成的值，否则它**必然**和实际不符。
> 快照点只有一个来源：`MANIFEST.md`。

**规矩：发快照的那一刻，等于承诺"之后不再改契约"。**

我们做不到这一点 —— 主仓库还在动。所以：

- 你手上的 `contracts/` 是**某个时刻的冻结版**；
- 如果你发现契约本身有问题（字段不够、语义不清），**不要自己改**，
  写一个 `issues/NNN-你的名字.md` 说清问题和你的建议，随活一起交回来；
- 如果你需要主仓库的最新契约，跟负责人要一份新包或 `git format-patch` 补丁。
  **别拿旧包硬撑** —— 我们踩过这个坑：有人差点照着一份过期 5 个提交的 `api.md`
  写完整套接口。

## 二、包里有什么（以及为什么）

| 目录/文件 | 是什么 | 你要不要看 |
|---|---|---|
| `docs/PARTNER-SHARED.md` | 你现在读的这份 | ✅ 先读完 |
| `docs/PARTNER-*.md` | 你的任务书 | ✅ 只读你自己那份 |
| `contracts/` | 数据与接口契约（**冻结**） | ✅ 你的活涉及数据就必读 |
| `data/out/*.jsonl` | 抓好的结构化数据 | ✅ 你的输入 |
| `data/raw/` | **46 MB 的网页与附件缓存** | ⚠️ 见下 |
| `collector/` | 抓取与解析代码 | 视任务 |
| `server/` `web/` | 后端与前端（别人在做） | ❌ 别碰 |
| `journal/` `issues/` | 团队日报与待决事项 | ✅ 了解一下背景 |

**`data/raw/` 是刻意放进去的（46 MB）。** 那是 315 个真实页面 + 124 个附件的原样缓存。
意思是：**你可以离线对着同一批真实页面开发解析器**，不用重新抓、不会因为网站改版
或网络问题而得到和别人不一样的结果。`.gitignore` 里忽略了它，但包里必须有。

## 三、你绝对不能碰的东西

| 不要动 | 为什么 |
|---|---|
| `contracts/**` | 契约是三个人的接口。改它 = 让别人半夜炸掉。有问题写 issue |
| 别人任务书里提到的目录 | 你俩的活是拆开的，交叉改必然冲突 |
| `.gitignore` 里的东西（缓存、`server/var/`） | 那些是运行时产物 |
| 任何"为了让测试通过"而改的断言 | 红了要查原因，不是改期望值 |

## 四、怎么把活交回来

**不要打包整个目录发回来** —— 那会覆盖别人的工作。用 git：

```bash
# 1) 先在包里提交你的工作（明确路径，不要 git add -A）
git add <你改的文件的明确路径>
git commit -m "伙伴X: 做了什么"

# 2) 打一个 bundle 发回来（一个文件，含你的提交历史）
git bundle create partner-X.bundle main

# 或者只要补丁，更小：
git format-patch <快照点> -o patches/
```

**交回来时必须写清：**
1. 你改了哪些文件（明确路径）
2. **你怎么验证的**（真实命令 + 真实输出，不要"应该没问题"）
3. 你**没做到**什么、哪里卡住了
4. 有没有动契约（正常情况应该是"没动"）

## 五、这个项目的一条铁律：不许猜数据

我们做的是**别人拿去做决定的信息**。所以：

- 抽不到就是抽不到，**填 `null` 并说明原因**，不要填一个"看起来对"的值
- 拿不准就标 `unsure` / `uncertain`，**不要为了答案整齐而猜**
- 报告里宁可写"我不知道"，也不要写一个没验证的数字

这条不是洁癖。我们已经因此改过三个真 bug：一个编造的截止日期、
一个把"本轮没抓到"显示成"公告被删除"的分类、一个把 id 变更报成"新增 30 条"的日报。
**错的信息比没有信息危险得多。**

## 六、做事方式（跟我们一样）

- **提交前必须跑测试**，红了不许提交
- **改动前先读文件**，不要凭猜改
- **每个坑写进注释**，说清"为什么"而不只是"是什么"——
  下一个人（或下一个 AI）能不能不重踩，取决于你有没有写下来
- 结论要能**追溯到证据**：数字、命令、输出、链接
